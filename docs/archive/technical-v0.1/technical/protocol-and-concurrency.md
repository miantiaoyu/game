# 协议、并发与恢复设计

> 历史设计，当前入口见[技术设计 v0.2](../../../technical-design.md)。

状态：技术设计提案，尚未实施。日期：2026-10-09。本文只定义接口、数据契约、并发语义和验收条件，不包含服务端、客户端或数据库迁移代码。

游戏规则以 [标准牌局规则 v1.0](../../../standard-rules.md) 为准。本方案暂按“网页房间，真人可以与机器人同桌”设计。行动计时、连接数量和资源限额是待原型验证的运行参数，不新增牌型、下注或改航规则。

## 1. 权威边界与部署范围

客户端采用 React、TypeScript strict 和 Vite，负责输入、展示、动画及连接恢复。服务端采用 Python 3.13、FastAPI、Pydantic 2、WebSocket 和 psycopg 3 异步连接池，数据库采用 PostgreSQL 17，在实现时固定具体补丁版本。数据库迁移通过显式版本管理，开发阶段可采用 Alembic；本轮不创建迁移。

服务器决定牌库顺序、底牌、合法动作、收费、下注上限、轮到谁、时间到后的合法代操作，以及全部结算。客户端不提交新余额、计算后的奖金、随机结果或“我已获胜”；客户端算出的牌型和动画结果不能修改权威状态。

MVP 为**一个服务进程、一个 Uvicorn worker**，一个房间只有一个 actor，整场只有这个 actor 能提交游戏状态。机器人进程仅计算建议，不能写数据库或直接执行动作。MVP 不需要 Redis、消息代理或分布式锁服务。

部署不允许同时启动两个应用实例；切换版本先停旧实例再启动新实例。启动时用专用 PostgreSQL 会话持有应用级单实例锁，第二实例拿不到锁就拒绝就绪。该连接不归还业务连接池；失去连接后整进程停止接收状态写入，完成状态确认和重新获取所有权后才能恢复。所有状态提交仍检查 state_revision，单实例配置不是省略数据库一致性检查的理由。

未来横向扩容改为“一个房间一个租约拥有者”，在每次数据库写入中检查递增 fencing token；旧拥有者即使尚未停止，也不能写入。Redis 可以承担路由或在线状态缓存，但不是租约真实性与账本正确性的唯一依据。此扩展不属于 MVP。

## 2. 运行参数建议

| 项目 | MVP 建议默认值 | 到达边界时的行为 |
| --- | --- | --- |
| 容量验证目标 | 100 个活跃房间、500 条 WebSocket 连接 | 达到目标前做压测；超出已配置准入上限的新房间或连接返回繁忙 |
| 一个房间的 FIFO mailbox | 64 个待处理事件 | 外部命令最多占用 56 项，保留 8 项给内部事件 |
| 单个连接的 JSON 帧 | 最多 16 KiB | 超限关闭连接，不解析成游戏命令 |
| WebSocket 框架入站缓冲 | 最多 4 条，每条最多 16 KiB | 网络背压与入口限流；不在框架里藏另一条无界队列 |
| 单连接待发送队列 | 最多 16 条消息或 64 KiB，总量任一先到即满 | 关闭慢连接；重连后获得完整快照 |
| 单次 WebSocket 写入 | 5 秒 | 写入超时关闭连接，不阻塞房间 |
| 每位玩家在同一房间的连接 | 最多 2 条 | 超出的新连接拒绝；只有一条能控制座位 |
| 单房间客户端连接 | 最多 10 条 | 超出时拒绝新订阅；容量控制不挤掉正常行动者 |
| 每连接命令速率 | 每秒 5 条，突发容量 10 条 | 超限命令在入队前返回限流；心跳不算游戏命令 |
| PostgreSQL 业务连接池 | 最少 2、最多 10 条 | 等待连接最长 1 秒，超时返回繁忙或进入恢复状态 |
| 数据库单次语句 / 事务目标上限 | 2 秒 / 3 秒 | 中止或确认提交结果；不跨长时间持有事务 |
| 机器人进程 | 专用 2 个，使用 spawn 启动 | 不与房间事件循环共享 CPU 密集计算 |
| 机器人待执行任务 | 最多 2 项执行、8 项等待，每房间最多 1 个有效任务 | 队列满时不继续堆积；到期执行合法保守代操作 |
| 机器人计算预算 | 每次建议 1.5 秒；不能超过对应行动期限 | 过期结果丢弃；失控工作进程按监督策略重建 |
| 下注行动期限 | 30 秒 | 无待跟注时过牌；有待跟注时弃牌 |
| 改航行动期限 | 20 秒 | 放弃改航，不扣改航费 |
| 局末展示 | 5 秒 | 到期进入下一局；整场结束则停留结果页 |
| 心跳 | 每 20 秒一次；10 秒内未应答视为连接失效 | 清理连接，不重置游戏行动期限 |
| 命令回执保留 | 房间存续期间，且关闭后至少 7 天 | 过期关闭房间仍不可恢复执行旧命令；房间 ID 不复用 |
| 回执内存缓存 | 每房间最多 256 项 | 缓存未命中回查数据库，不能把缓存淘汰当作没执行过 |
| 房间公开事件缓存 | 最多 128 条或 128 KiB | 丢弃最旧缓存，持久事件与恢复状态仍在数据库 |
| 客户端本地历史 | 最多 256 条，先渲染最近 50 条 | 按需分页；不把历史加进每次快照 |

限额是可配置运行参数，需要随 CPU、数据库和原型负载验证。日志、指标与管理端不占用玩家协议中的消息队列。客户端的 resync 与回执查询也要限流，避免把读请求变成另一条无界入口。

## 3. 一个房间怎样顺序执行

每个房间 actor 维护当前**已提交**状态、连接订阅、最多一个当前有效行动期限，以及最多一个有效机器人任务。房间注册表以共享创建任务的方式完成首次加载：同一房间的两个同时加入请求等待同一加载结果，不能各自创建一个 actor。

网络接收任务只负责认证、大小检查、协议解析、限流及非阻塞入队，不直接改筹码。成功入队的事件由 actor 按 FIFO 顺序逐个处理；检查、推导候选状态、提交、替换内存状态这一段对本房间始终只有一个执行者。不同房间可并行等待数据库，不共享游戏状态锁。

事件包括玩家命令、控制权变更、行动到期、机器人计算结果、订阅与取消订阅、恢复完成。内部事件使用同一 FIFO，不因“系统事件”身份插队；单独保留容量是为了让超时与故障恢复能进入队列。每个 turn 最多挂一个定时任务、一个机器人结果生产者，取消后不得继续产生重试风暴。

外部命令使用 `put_nowait` 语义：成功入队时记录服务器单调时钟时间和本房间的 admission 序号；队列达到外部限额则立即返回 `SERVER_BUSY`，没有接受也没有执行该命令，客户端可以用同一 command_id 重试。不能先回复“收到”，再无限等待入队。

入队时间用于活进程内的先后与期限判定，**入内存队列不是持久成功回执**。若进程在命令提交前崩溃，浏览器重试时必须按恢复后的权威状态重新判定；MVP 不承诺保存尚未提交命令的原 admission 时间。需要跨崩溃保留这项权利时，应另设计持久 inbox，不能仅靠内存队列宣称具备该保证。

内部事件用保留容量；极端情况下总队列也满，唯一对应生产者异步等待空位，不丢弃关键事件，不自旋重试。尚未入队的内部事件不能抢到已成功入队玩家命令之前。即使定时事件暂未排入队列，所有玩家动作仍独立检查期限，超时玩家不能利用调度延迟继续行动。

actor 空闲时等待 mailbox 或明确的恢复信号，不循环查询当前时间、不轮询数据库。只有一个活动期限定时器；建立新行动机会时取消旧任务并使用新 turn_id。恢复同一机会的定时任务沿用已持久化的 turn_id 与期限。取消未及时生效也无妨：过期事件必须再次验证 turn_id。

### 同一次转移的确定性工作

纯规则部分接收当前状态与一条已验证动作，返回候选状态及事件。自动推进——例如下注轮关闭、退款、形成并冻结改航名单、揭牌、创建下一个行动机会——在候选状态内完成，直到遇到下一个需要玩家输入的点或局末展示点。

不能让两个协程各自执行“下注结束就揭下一张牌”。这些自动转移属于同一次 actor 处理，使用同一候选状态，一次提交，只有提交后的结果能对外展示。动画持续时间不参与规则执行；浏览器动画慢不会拖延其他玩家的逻辑状态。

## 4. 标识与版本

| 标识 | 含义与约束 |
| --- | --- |
| room_id | 房间生命周期标识；关闭后永不复用 |
| match_id | 一整场最多 12 局的标识；在同房间开始新整场时更换 |
| principal_id | 已认证真人或已配置机器人身份，由服务器从凭证确定 |
| seat_id | 本场座位 0—4，由房间成员关系决定，客户端不得通过 payload 指定代他人行动 |
| command_id | 客户端生成的唯一命令标识；同一次用户意图重试保持不变 |
| state_revision | 房间生命周期内单调递增的权威状态版本，跨 match 不重置；通过 JSON 十进制字符串传输 |
| turn_id | 一次具体行动机会初建时生成并持久化的 UUID；同玩家因加注再次响应也产生新值，不从 state_revision 推导 |
| event_seq | 房间持久事件序号；一次 state_revision 可含多个事件，序号单调递增 |
| controller_epoch | 同玩家在本房间控制权的代数；成功切换控制连接时增加，JSON 十进制字符串 |
| connection_id | 单条 WebSocket 的服务器标识；断线重连产生新值，不当作玩家身份 |
| tab_id | 浏览器标签实例标识，只辅助同用户控制权和界面提示，不授予权限 |
| stream_id | 本次订阅流标识；客户端忽略已替换连接或旧 stream 的迟到消息 |
| ruleset_id / ruleset_version | 标准值为 `dark-tide-standard-1.0` / `1.0`；确定规则身份及其版本，整场固定 |
| protocol_version / state_schema_version | 分别固定通信协议和持久快照格式；不可与规则版本混用 |

state_revision 不只用于“轮到谁”的判断，还避免依据旧的池、余额或公开牌操作。turn_id 防止旧动作落到同一玩家的下一次机会。match_id 防止上一场的动作落入下一场。controller_epoch 防止旧标签在交接后继续发新命令。这几个检查解决不同问题，不能互相替代。

state_revision 位于外层 RoomSnapshot，不在 MatchState 中维护第二份版本。准备状态、开局、游戏动作、控制权变更等已提交状态转移都会增加它；断线、重连显示和心跳等临时 presence 状态走独立通知，不增加它。请求中的 expected_revision、回执中的 applied_revision 都指同一份 state_revision。

认领当前 turn 的控制权会增加 state_revision 和 controller_epoch，**不改变**该机会已有的 turn_id 与 deadline_at；持有旧 expected_revision 的新动作会被拒绝。只有新的行动机会才生成新 turn_id，不能因任意 state_revision 变化、订阅或重连而重新计时。

JSON 中所有筹码、位置、局数与费用均为严格整数，不接受浮点数、布尔值当整数、NaN、负筹码或字符串金额。state_revision/event_seq 用字符串避免 JavaScript 整数精度问题。服务器最终仍按规则验证每个金额的合法范围。

## 5. 命令协议草案

以下 JSON 是协议样例，不是实现代码。浏览器通过一个已认证 WebSocket 订阅一个房间；服务器从连接绑定 principal_id，不相信客户端自称的身份。

### HTTP 入口与访客身份

| 入口 | 输入与权限 | 返回及约束 |
| --- | --- | --- |
| `POST /api/v1/guest-sessions` | 昵称；已有有效会话时复用当前身份 | 新建或恢复 principal_id，设置同源 Secure、HttpOnly、SameSite 会话 Cookie；昵称仅用于展示，不作为登录凭据 |
| `POST /api/v1/rooms` | 已认证身份、command_id、允许的房间显示配置 | 创建房间并返回 room_id；建房以 `(principal_id, room.create, command_id)` 查创建回执，回执与房间同事务保存，重试不能重复建房 |
| `POST /api/v1/rooms/{room_id}/memberships` | 已认证身份、command_id、邀请口令（如需） | 经房间 actor 创建成员关系或返回原结果；不允许抢占已绑定席位，进行中只能按产品许可成为观众 |
| `GET /api/v1/rooms/{room_id}/state` | 有效房间访问权限 | 返回调用者自己的完整 viewer 快照，可用于首次加载或恢复；不能指定其他人的 viewer 身份 |
| `GET /api/v1/rooms/{room_id}/public-events` | 房间访问权限、事件游标、分页条数 | 返回按权限公开的历史；默认 50 条、最多 100 条，仅按 event_seq 分页，不提供原始私密事件 |

Cookie 内是不可猜测的会话令牌，服务器保存其摘要、principal_id、到期和撤销状态；这些身份数据持久化在 PostgreSQL，因此 API 进程重启不会更换同一浏览器的玩家身份。状态写入接口校验 Origin 与 CSRF 防护，令牌不进 URL 或日志。清除 Cookie、主动退出或凭据过期后，纯访客模式不保证找回原 principal、席位和私牌；输入相同昵称不能夺回身份。跨设备账户找回不属于 MVP。

HTTP 修改入口也通过相同授权、去重与 actor/事务边界，不能绕过 WebSocket 使用另一套写状态流程。创建房间前的创建回执属于 principal 级独立命名空间；房间存在后的命令统一使用第 6 节的房间回执键。只读 HTTP 快照不替代 WebSocket 建立订阅时的有序初始快照。

### 房间内命令

```json
{
  "type": "command",
  "protocol_version": 1,
  "command_id": "a672e7cc-4035-4cda-89be-44ffce7fbab8",
  "room_id": "509451ec-1849-4760-a841-05b9fbbd33ad",
  "match_id": "575ec353-086b-4503-ae82-7dc6b47dbfb1",
  "expected_revision": "83",
  "turn_id": "2d953558-54d7-4ab3-b15b-fe1c07bbfb51",
  "controller_epoch": "4",
  "command": "bet.raise",
  "payload": { "add_chips": 16 }
}
```

`add_chips` 明确为**本次新增投入，包含跟注额**，与标准规则一致；不叫含糊的 amount 或 raise_to。改单个公共牌位置用 `slot: 0 | 1`，不提交牌 ID。名单、收费与随机补牌由服务器决定。

| 命令族 | 请求字段 | 校验重点 |
| --- | --- | --- |
| `bet.check` | 空 payload | 本人当前行动、无待跟注额 |
| `bet.call` | 空 payload | 服务器计算实际补齐额或合法不足额全下 |
| `bet.fold` | 空 payload | 当前有待跟注额，不能无条件主动弃牌 |
| `bet.raise` | add_chips | 加价权、最低完整加价、合法短额全下、底池上限、余额 |
| `swap.replace` | slot 为 0 或 1 | 当前改航机会、被冻结报价、足额余额、最新公共牌面 |
| `swap.pass` | 空 payload | 当前改航机会；推进后不能补做 |
| `controller.claim` | tab_id、expected_controller_epoch | 身份与席位合法，原 epoch 匹配；不占用游戏动作机会 |
| `room.ready` | 本人的 ready 布尔值 | 真人成员仅能在 WAITING 修改自己的准备状态，不能替别人准备 |
| `room.set_bots` / `room.start` | 机器人补位设置或空开局 payload | 仅房主在合法准备阶段使用；开局核对真人准备与五席完整性，不接受任意规则对象 |
| `state.resync` | 最近看到的 state_revision 可选 | 只读，返回当前 viewer 的完整快照，不执行旧动作 |
| `command.status` | 被查询的 command_id | 只允许查询自己的回执；查询本身不生成命令回执 |

房间配置命令不需要 turn_id；同一判别联合不能允许下注命令漏掉 turn_id。Pydantic 使用明确命令类型与字段白名单，未知字段和未知命令拒绝。客户端 TypeScript 联合类型来自同一份协议规范；前端编译期类型不能代替服务器运行期验证。

### 回执

```json
{
  "type": "command.result",
  "command_id": "a672e7cc-4035-4cda-89be-44ffce7fbab8",
  "status": "applied",
  "applied_revision": "84",
  "result": { "action": "raise", "paid_chips": 16 }
}
```

业务拒绝的 status 为 `rejected`，包含稳定错误码，例如 `REVISION_MISMATCH`、`TURN_MISMATCH`、`NOT_CONTROLLER`、`ILLEGAL_ACTION`、`TURN_EXPIRED`。当前房间版本可作为帮助同步的元数据，但不返回别人的底牌或内部验证细节。

`SERVER_BUSY`、未认证、格式错误和帧过大在正式处理前拒绝，不声称已经接受或提交；其中繁忙可用原 command_id 重试。已持久化的业务拒绝是该 command_id 的终态；玩家基于新状态发起新的合法意图时必须生成新 command_id。

浏览器只维护一个“待确认意图”，在收到回执前不自动重复生成新 ID。断线时状态显示为“等待确认”，重连先查询或重发相同命令。收到旧命令回执不能把画面回滚到 applied_revision；只有权威快照驱动状态，且同房间版本不能倒退。

## 6. 幂等：先识别重复，再判断过期

已创建房间内的回执唯一键为 **(room_id, principal_id, command_id)**。match_id 被纳入语义内容，避免同房间跨整场复用一个命令 ID 被误当新命令。

payload_hash 来自经协议规范化后的语义 JSON，包含协议版本、房间/整场、命令类型、payload、expected_revision、turn_id、controller_epoch；不包含传输时刻、连接 ID、网络重试次数。对象键顺序不影响 hash；未知字段在规范化前就拒绝。hash 不作为身份认证，也不替代金额校验。

处理顺序必须是：

1. 认证连接，确认该身份可访问房间，解析与限制消息大小。
2. 查找该身份该 command_id 的已提交回执。
3. 已存在且 hash 相同，直接返回原结果；已存在但 hash 不同，返回 `IDEMPOTENCY_CONFLICT`，禁止执行。
4. 尚不存在，才检查当前 controller_epoch、match_id、state_revision、turn_id、成功入队时间与行动期限。
5. 验证规则、推导候选状态，事务写入状态、事件和回执。
6. 确认提交完成后更新内存并回复、广播。

例如加注已扣款并推进到新 turn，但 ACK 丢失。客户端重发原请求时，expected_revision 和 turn_id 都已过期；由于重复检查先做，服务器返回原成功回执，不再次扣款，也不错误地将成功动作解释成失败。

控制权已经转移时，旧标签仍可在认证和房间访问有效的前提下查询自身历史回执，但不能执行新的动作。返回历史结果不等于恢复旧控制权。访问已被撤销的身份不能通过“重复命令”绕过授权。

## 7. 提交顺序与未知提交结果

每条会改变持久状态的命令先构建独立候选对象。当前 actor 的已提交状态、牌库游标和余额都不原地修改。仅当数据库事务成功后，才将内存指针切换到候选状态。

一次事务原子地完成：检查房间 state_revision、写入下一版本快照、追加领域事件、写入成功回执；控制权切换等成员表更新也在同一事务中。业务拒绝通常只写拒绝回执，不增加游戏状态 state_revision。数据库唯一键和 compare-and-swap 条件是最终防线，不能仅靠进程内 dict 去重。

只有 **commit 之后** 才回复成功和排入广播。actor 不等待 WebSocket 发送完成；每个连接自己的 sender 消费出站队列。提交成功但广播失败时，数据库已生效，连接重建后从快照恢复。

如果数据库明确回滚，丢弃候选状态，保持已提交内存状态，返回可重试的暂时失败。若超时或连接断开导致“不知道 commit 成功没有”，本房间进入恢复中，暂停继续执行队列里的写命令：

- 不发成功，不发确定失败，也不直接把候选状态再扣一遍钱。
- 用新数据库连接查原 command_id 回执和房间版本。
- 找到已提交回执，加载对应的最新权威状态并返回原结果。
- 回执暂时不存在时，不能立即推断原事务失败；原事务可能还在结束。确认旧事务已结束，或在新事务中以相同唯一键、原 expected_revision 再次判定，让数据库锁与唯一约束裁决。
- 确认未提交后，允许同一命令重新进入正常处理；如果不能确定，继续标记恢复中并保持期限状态，不猜测结果。

数据库连接池耗尽、语句超时、连接中断必须有上限和退避。恢复等待只阻塞相关房间；不能持有全局注册表锁或独占全部数据库连接。服务故障必须明确显示为恢复中；期限按第 10 节继续处理，恢复时已过期的行动执行合法 timeout，MVP 暂不承诺停机补时。

## 8. 持久字段设计，不生成 SQL

以下为逻辑表和字段要求，实现时再形成迁移。读写快照与事件的数据库角色仅服务端持有；浏览器和机器人工作进程没有数据库凭证。

`RoomSnapshot` 是一次提交的一份完整逻辑状态：房间头部（room_id、RoomStatus、state_revision、state_schema_version）、当前整场引用及不可变规则引用、可空 MatchState、当前等待机会（turn_id、行动席位、deadline_at）、成员席位/准备/控制权绑定，以及 last_event_seq。Socket、presence、mailbox、运行期单调时钟和任务句柄不在快照中；protocol_version 属于消息封套，不是另一份牌局状态。

物理保存时，头部、整场/规则引用与当前期限写到 `rooms` 类型列，成员写 `room_members`，MatchState 的公开/私密载荷分别写 `state_public` / `state_private`；所有部分在同一事务写入并合成为一份 RoomSnapshot。**JSON 载荷不再另存可独立修改的房间 status、state_revision、turn_id 或 deadline_at。** MatchState 的 match_id、ruleset_id、ruleset_version 由对应类型列构造为不可变上下文；如果为归档冗余编码这些值，只允许由同一序列化器生成，加载时不一致即判损坏，禁止“任选一份为准”。派生索引、投影视图和 matches 结果索引均从这份提交生成，不能充当第二个账本。

### rooms：当前权威快照与生命周期

| 字段 | 类型概念 | 约束或用途 |
| --- | --- | --- |
| room_id | UUID | 主键，永久不复用 |
| status | RoomStatus 枚举 | `WAITING / STARTING / PLAYING / RESULTS / CLOSED`；数据库与 wire 使用这些固定大写字符串，恢复中只是运行状态覆盖层 |

| ruleset_id / ruleset_version | 文本 | `dark-tide-standard-1.0` / `1.0`；整场内不可悄悄更改 |
| state_schema_version | 整数 | 服务端持久格式迁移版本 |
| state_public | JSONB | 公共牌、筹码、阶段、普通贡献、冻结报价与费用记录等持久事实；派生池结构与合法金额范围按规范重建，不保存多份可独立修改的总数 |

| 字段 | 类型概念 | 约束或用途 |

| ready | 布尔值 | WAITING 阶段的准备状态；通过房间命令修改，不能从在线 presence 推断 |

| controller_tab_id | UUID，可空 | 最近控制标签标识 |

同账号多标签可以看到自己的私牌，只有当前控制连接能提交新的游戏动作。epoch 持久化；连接在线与否是短暂运行状态，不能从数据库旧 connection_id 推断重启后的活连接。

| 字段 | 类型概念 | 约束或用途 |
| --- | --- | --- |
| room_id + event_seq | UUID + 64 位整数 | 联合主键，每房间单调追加 |
| state_revision / match_id | 版本 + UUID | 所属提交与整场 |

每次状态快照与事件一起提交，恢复通常直接读快照，事件用于审计和重建校验。领域事件不是客户端广播 DTO；不能把数据库事件整行序列化后发给浏览器。

| 字段 | 类型概念 | 约束或用途 |
| --- | --- | --- |

## 9. 同一人的多标签控制

第二个标签默认只读地显示同一个玩家视角，并展示当前控制标签已存在。用户执行“在此接管”后提交 `controller.claim`，附当前 expected_controller_epoch 和房间 state_revision。

actor 成功提交后增加 epoch、绑定新 connection_id、推送新快照，并通知旧标签变为只读。两个标签同时基于 epoch 4 接管，只有一个能提交为 epoch 5，另一个收到版本或 epoch 冲突并同步；不能两者都声称控制成功。

普通动作必须匹配当前 connection_id 与 epoch，不能只验证“是同一个账号”。旧标签在接管前已成功提交的动作仍然有效；已入队但在接管后才轮到处理的新动作会被拒绝。到底谁先发生由 actor FIFO 与事务提交决定，不依据浏览器时间戳。

断线不更换身份、不替用户弃掉整场、不挪动按钮，也不重置行动期限。重连取得视图后认领控制权；认领本身不是游戏动作，不让玩家获得额外改航机会。即使接管成功，已经过期的 turn 也不能复活。

## 10. 行动期限、断线与定时器竞争

服务器在建立新行动机会时，同时提交 turn_id、acting_seat、deadline_at。客户端收到 deadline_at 和服务器时间，仅绘制倒计时；浏览器自己的时钟或动画不能决定动作是否到期。

活进程内部以单调时钟比较期限，客户端动作以**成功入队时间**为准，规则为 `enqueued_at < deadline` 才按时。等于期限视为过期。网络已到内核但尚未通过限流/验证/成功入队，不算已受理。服务器不接受客户端自报的发送时间。

定时器到期后把 `turn.timeout(turn_id)` 放入同一 FIFO：

- 玩家动作先成功入队且未过期，即使数据库等待让它在期限之后才处理，也仍有效；随后旧 timeout 因 turn_id 不符失效。
- 动作在期限之后入队，即使定时任务因调度延迟尚未处理，也返回 `TURN_EXPIRED`，不能延长窗口。
- timeout 先提交并推进 turn，迟到玩家动作不再生效。
- 重复 timeout、取消未及时完成的旧定时任务，均先检查 current turn_id 与期限状态，不能触发第二次过牌、弃牌或下一局。

正常网络断线继续使用同一期限。到期时的服务代操作只从标准规则已有动作选择：可免费过牌则过牌；有待跟注额则弃牌；改航阶段放弃。不会自动替真人付费改航、主动加注、补充筹码或替全下者弃牌。全下者本就没有普通行动 turn，不应为其创建下注超时。

系统整体停机与个人断网分开处理。服务恢复时先加载原有期限；未过期则按剩余时间继续，已过期则提交对应合法 timeout 并前进，不给每次重启都附加完整 30 秒。若产品后续要求运维停机补时，应作为显式服务暂停事件持久化并向全桌展示，不能后台悄悄改 deadline。

UTC deadline 用于持久恢复，monotonic 值不能跨进程保存。恢复时根据当前 UTC 与当前单调时钟重建剩余时间；活进程不因系统墙钟微调重新延长已建立的期限。监测到严重时钟异常或数据库长期不可用，进入明确的服务恢复状态，避免猜测顺序或暗中结算。

## 11. 按 viewer 投影，而不是发送原始状态

在每次提交后，actor 根据该连接已认证的 principal_id 和成员角色调用纯投影函数。所有对外数据采用白名单 DTO，禁止对整个内部状态通用 JSON 序列化。

| 数据 | 本人玩家视角 | 同桌其他玩家 / 观众 | 机器人任务 |
| --- | --- | --- | --- |
| 本人的两张底牌 | 本人可见，正式摊牌前不向别人显示 | 仅按规则正式摊牌时显示未弃牌者底牌 | 仅该机器人自己的两张底牌 |
| 对手底牌 | 正式摊牌前仅张数/牌背 | 同左 | 不提供；由策略根据可见信息抽样 |
| 弃牌者底牌 | 本人可看自己的；不公开他人的 | 保持隐藏，整场结束也不自动公开 | 不提供 |
| 完整牌库、抽牌游标、随机内部状态 | 不提供 | 不提供 | 不提供 |
| 公共牌、公开弃牌、筹码、普通池/附加池 | 可见 | 可见 | 作为公开观察提供 |
| 改航名单、冻结报价、公开动作顺序 | 可见 | 可见 | 提供允许使用的公开观察；模型是否据此推断是独立能力 |
| 合法动作与金额范围 | 当前可控制座位的合法操作 | 不授予他人操作能力 | 仅该机器人的合法动作范围 |

如标准规则要求直接结算而无须摊牌，不能为了“结算动画”公开赢家底牌。只有需要比较牌型而正式摊牌时，公开所有仍未弃牌玩家的两张底牌。历史记录、回放和错误消息遵循相同边界。

MVP 每次权威变更发送完整 viewer 快照，消息类型为 `state.snapshot`，带 room_id、match_id、state_revision、stream_id、server_time、stage、公开桌面、该 viewer 的私有字段、当前期限与合法动作。动作摘要只用于动画，不承担状态重建责任。快照不包含无限历史，保证单帧上限；历史分页使用单独受鉴权接口。

| 快照字段组 | 内容 | 协议注意点 |
| --- | --- | --- |
| envelope | protocol_version、room_id、match_id、state_revision、stream_id | state_revision 是十进制字符串，不暴露内部对象引用 |
| public_table | 固定五席、余额、普通贡献、公开状态、公共牌、公开弃牌、各池资格与金额 | 未公开底牌只给 card_count，不给 CardId 或可猜测编码 |
| self | 本人 seat_id、本人两底牌、controller_epoch、is_controller | 观众不提供私牌字段；只读同账号标签仍属于本人视角 |
| current_turn | acting_seat、turn_id、phase、deadline_at、server_time | 无需输入时为空；不通过客户端 tick 修改权威 deadline |
| legal_actions | 判别联合、可新增投入范围、跟注实际金额、是否有加价权、改航固定价格 | 仅当前合法控制者或机器人获得可执行操作；金额以服务器为准 |
| presentation | 最近本次提交的公开动作摘要和事件序号 | 可跳过动画，不影响状态；不能塞入全部历史 |

MVP 客户端不需要离线重放领域事件。重连直接请求完整当前快照；以后若增加增量补发，必须基于 viewer 投影后的事件和连续 state_revision，不能把原始私密事件流暴露出去。

## 12. WebSocket 背压与重连

每条连接有独立 sender 和有界出站队列。actor 只做非阻塞排队，不能在房间循环内等待慢浏览器、网络写入或动画确认。出站累计超过 16 条或 64 KiB 即终止该订阅，关闭码采用可重试的服务繁忙语义；客户端使用带抖动退避重新连接。

不在无界内存中为断线客户端保留广播，也不随机丢中间事件后假装连续。已提交状态安全保存在数据库；重连重新认证、加入 actor 订阅并获取完整快照。

订阅建立也通过 actor 顺序处理：先为该连接登记订阅并排入当前快照，之后的提交才排后续快照。这样不会发生“读完快照到订阅之间漏掉一次下注”。处理重连时不持有事务等待连接发送。

客户端以 room_id、match_id、state_revision 和 stream_id 管理状态；旧 WebSocket 的迟到消息不得覆盖新连接数据。MVP 的完整快照可以跨版本号直接替换旧快照，不需要因为跳号而 resync；ACK 已收到而对应或更新快照未到时保留等待同步状态。未来若启用增量消息，增量缺口才需要 resync。多次重连、刷新和命令重试均不再次扣筹码。

认证建议使用同源 HttpOnly 会话 Cookie，验证 WebSocket Origin，房间邀请口令只用于加入而不等于玩家身份。不要把长期凭证放进 URL 查询参数或日志。房间内操作权限、控制连接权限、规则合法性是三道不同检查。

## 13. 机器人：计算在外，决定仍在 actor

房间创建机器人任务时，冻结该机器人的 viewer 观察和任务标识，包含 room_id、match_id、state_revision、turn_id、bot seat、合法动作范围及任务截止时间。只把序列化后的观察发给专用 spawn 进程池；不得把 actor、数据库连接、完整内部 State、真实牌库或其他人的底牌传进去。

进程池以 spawn 创建，避免通过 fork 继承当前服务进程内的房间牌库。工作进程入口仅初始化策略和任务通信，不加载服务凭证或数据库连接；必要时过滤启动环境。机器人采样使用独立随机流，不能复用或获知真实洗牌随机源。

计算结果回到 actor mailbox，作为“动作建议”处理。actor 重新检查机器人身份、match_id、turn_id、当前状态版本、合法动作和截止时间。只要机会已结束、房间已恢复到其他版本、任务过期或已执行过，就丢弃结果；结果本身不能覆盖新状态。更新控制元数据造成 state_revision 变化时，宁可取消并重算或等待合法超时，也不把旧估计无条件套到新状态。

每房间最多一个有效任务。新 turn 到来时取消旧任务标识；进程中正在运行的计算未必能即时停止，但其结果已失效。工作进程超过硬预算时监督器终止/重建该进程，不能无限累积失控计算。队列满时不阻塞 actor，到期限仍无法提供有效建议则执行合法保守代操作。

现有机器人是局部概率启发式：会响应最新公共牌，但不因此自动具备从“谁改了什么”推断对手手牌的能力。实现本协议不能将它宣传成完成了心理信号建模；策略能力升级与协议正确性分开验收。

## 14. 崩溃恢复与秘密牌库

服务启动后按需恢复房间，首先读取最后提交的 snapshot、state_revision、event_seq、ruleset_id、ruleset_version、控制权代数和期限。不能因为内存为空就重新发牌、补筹码、重新确定按钮或重新洗当前局。

每局产生新的完整随机牌库后，**在任何人看到这局底牌或公共牌之前**，将完整排列、各玩家实际底牌、已抽位置以及局面变更一起持久化。恢复继续消费已保存的排列。只保存一个“下次再随机抽牌”的标记不够；只保存依赖某个 Python 版本算法的 seed 也不够稳妥。

如果首局洗牌事务未提交，任何底牌都不能发送；如果已提交但发牌消息丢失，重连通过投影显示原来的底牌。失败的候选状态不对外可见，未知提交必须先查询回执确认，不重新抽一个结果尝试替代。

服务恢复时解除旧连接绑定，保留成员身份与 epoch；连接重新认领时生成新的控制权代数。恢复过程不向观众返回底层快照，不通过调试响应泄露牌库。

不支持的 ruleset_id / ruleset_version 或 state_schema_version 不可强行按新逻辑继续。该房间显示恢复中，进入明确的迁移或人工排障流程。无需为了版本迁移在 MVP 中重放全部历史；已提交快照与事件范围能够校验即可。

## 15. 避免死锁与无界等待

- 每个房间只有 actor 能写游戏状态，不再叠加“房间锁＋玩家锁＋牌库锁”。外部任务只能发消息。
- actor 可以等待一次有上限的数据库事务，但不能在事务中等待 WebSocket、机器人、用户输入或另一个 actor 的回答。
- 数据库连接只在事务或短查询期间借用，不能把一条业务池连接绑在房间上。单实例所有权专用连接另计。
- 多行写入统一采用房间行、成员行、事件/回执的固定访问顺序；控制权接管和游戏动作不能互相倒序加锁。
- 房间加载注册表不在持有全局锁时等待数据库。以一个共享加载 future 避免重复初始化，失败后明确清理。
- 不在 actor 中提交机器人任务后等待其结果。任务完成走 mailbox；队列与超时都有边界。
- graceful shutdown 先停止新连接与新命令准入，等待当前有限事务结束或进入结果确认，随后保存已提交状态并关闭。未提交动作不回复成功；客户端重连用相同 command_id 解决不确定性。

## 16. 故障验收清单

这些是后续实现必须验证的场景，当前设计阶段不新增测试代码。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 同一 command_id、相同 payload 发送十次 | 恰好一次规则效果，所有可重试查询返回同一终态 |
| 同一 command_id 改金额重发 | `IDEMPOTENCY_CONFLICT`，不执行第二个金额 |
| 扣款 commit 成功，ACK 前进程退出 | 重连看到已扣一次筹码，原命令返回原成功回执 |
| 候选状态构建后数据库明确回滚 | 公共牌、余额、牌库游标和 state_revision 都不改变 |
| commit 返回前连接丢失 | 房间先确认回执和事务状态，不盲目宣布失败或再次扣款 |
| 两个标签同时发送当前 turn 动作 | 至多一个提交；另一个按控制权、turn 或 state_revision 明确拒绝 |
| 两个标签同时认领同一 epoch | 只有一个成为新控制者，旧连接不能发新的有效动作 |
| 成功动作重试时 state_revision 已推进 | 返回原成功回执；不因 stale 检查先执行而误报失败 |
| 玩家动作 deadline 前成功入队，actor 处理时已过期 | 若此前无人推进 turn，动作有效；随后旧 timer 不重复代操作 |
| 玩家动作 deadline 后入队，timer 尚未消费 | 动作过期，不利用调度延迟获利 |
| 旧 turn 定时器在新 turn 到来后触发 | turn_id 不匹配，无效果 |
| 当前玩家断线又重连 | 期限继续，筹码与私牌保持，未完成意图通过回执确认 |
| 整体服务重启，期限已经到期 | 恢复原牌库和原 turn，执行一次标准合法代操作，不重置完整计时 |
| 当前局曾经改航后重启 | 公开弃牌、补入牌、后续牌库位置与重启前一致 |
| 慢客户端一直不读消息 | 其连接被断开，其余房间/玩家继续；内存不随事件数增长 |
| mailbox 外部额度已满 | 新动作立即繁忙；timeout 和恢复事件仍可通过保留额度入队 |
| 旧机器人结果在下注或改航机会结束后到达 | 丢弃，不覆盖新公共牌、金额或 turn |
| 机器人进程崩溃或耗时超预算 | 房间循环仍响应连接；到期安全代操作，不出现无限等待 |
| 玩家、观众、机器人观察同一局 | 每个视角只含其允许字段；无其他玩家未公开底牌或真实牌库 |
| 弃牌者底牌在回放、错误和日志中检查 | 除本人合法视图外保持隐藏，不因调试或结算泄露 |
| 意外启动第二服务实例或第二 worker | 就绪前拒绝，不允许双 actor 写同房间 |
| 一房间故障或数据库短暂拥塞 | 不持有全局房间锁；其他房间不因它等待网络或机器人结果 |

进入实现阶段前需要把接口名称、错误码和字段表定为版本化契约，并明确机器人可见观察与前端快照的共同测试样本。原型优先展示正常行动、改航顺序、等待确认、断线恢复及接管控制权这些状态；不能用乐观扣筹码掩盖协议未确认的结果。

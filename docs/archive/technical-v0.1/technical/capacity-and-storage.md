# 空间、内存与容量预算

> 历史 Python／网页容量估算，当前设计见[技术设计 v0.2](../../../technical-design.md)。

状态：工程设计估算，未运行新服务压测或测量其进程内存。规则范围固定为标准 v1.0；工程限额与超时是建议配置。

## 1. 先确定数据数量的硬边界

| 数据 | 上限或范围 | 原因 |
| --- | --- | --- |
| 固定座位 | 5 | 淘汰后不压缩编号 |
| 牌库 | 27 个 CardId，取值 0—26 | 三种花色，各 1—9 |
| 玩家底牌 | 最多 10 张 | 五人各两张 |
| 当前公共牌 | 最多 3 张 | 逐张揭开 |
| 同局公开换出牌 | 最多 5 张 | 每人最多改航一次 |
| 每局消耗的牌库牌数 | 最多 18 张 | 10 张底牌＋3 张原始公共牌＋最多 5 张替换牌 |
| 存活或资格名单 | 5 位掩码，范围 0—31 | 每个位对应固定座位 |
| 已知牌集合 | 27 位掩码，放入 32 位容器 | 集合测试、互斥与未知牌采样 |
| 单人余额、贡献、池金额 | 0—500 枚 | 整场筹码总量 500 |
| 原始普通贡献层 | 最多 5 层 | 每人一个最终普通贡献额，最多五个非零断点 |
| 本局改航费用记录 | 最多 5 笔 | 每人一次；资格合并后池数不会增加 |
| 冻结报价 | 最多 5 条 | 报价后不重新排列 |
| 整场局数 | 最多 12 | 提前结束可更少 |

牌库可保存为完整排列与读取游标。底牌、公牌、弃牌记录引用已消耗的 CardId；这些字段与排列前缀在存储中会重复表示同一张牌，不能错误地要求所有字段连同完整牌库一并互斥。真正的互斥约束是“当前底牌＋当前公牌＋公开弃牌＋未消耗牌库后缀”恰好覆盖各自应有的唯一牌；尚未发给淘汰席位的牌不从牌库移除。

## 2. 逻辑位宽与 Python 真实对象分开算

| 值 | 紧凑表示的逻辑需求 | 首版 Python 表示 | 对外／数据库 |
| --- | --- | --- | --- |
| CardId | 1 字节 | int，牌库可用 bytes 或 bytearray | JSON 整数；未公开牌为 null 或 card_count，不传隐藏 ID |
| SeatId／资格掩码 | 1 字节 | int | JSON 整数或可读座位数组，按协议统一 |
| 筹码 | 2 字节即可覆盖 500 | int，严格拒绝浮点、负数和 bool | JSON 整数；独立金额列可用 SMALLINT 加范围约束 |
| 三张牌强度编码 | 2 字节足够 | 小整数或 uint16 查表 | 仅需要时投影牌型描述 |
| 状态枚举 | 1 字节逻辑值 | 共享 Enum 实例 | 稳定字符串，不能暴露枚举声明顺序 |
| revision／事件序号 | 64 位整数 | int | PostgreSQL BIGINT；JSON 使用十进制字符串，避开 JS 安全整数边界 |
| turn_id／command_id／实体 ID | UUID 16 字节 | UUID 或规范化字符串 | 数据库 UUID；JSON 字符串 |
| 时间戳 | 64 位时间值 | 明确 UTC 时间与运行期单调时间 | TIMESTAMPTZ／ISO 8601 字符串 |

不能把“5 个筹码值只要 10 字节”当作 Python 对象的真实占用。列表、元组、对象头、引用、整型对象、字符串和事件包装都有开销；slots 只减少实例字典，不把 Python 自动变成紧凑 C 结构。

本局卡牌、筹码、轮次、报价和至多十个池的**逻辑定长载荷可以控制在 1 KiB 内**；这不含 UUID、日志、用户资料及 Python 对象开销。首版为一份完整 Python 领域状态预留 **8—32 KiB**，编码为 JSON 的私有持久化快照目标 **不超过 16 KiB**。这些是待测预算，达到前不能据此宣称容量。

快照包括恢复所需的牌库顺序、底牌与当前待动作状态，不能为了省空间删除必要的私有数据。socket、锁、任务、随机生成器对象和头像不进入快照。

## 3. 小数组与掩码优先，避免无界容器

座位相关数据使用固定长度五项结构，按 SeatId 索引；不把用户 UUID 当作每次下注循环的键。姓名、头像、连接会话放在房间元数据，领域状态仅保存座位关联。

最多五人的动作顺序、报价与池，线性扫描就足够。没有必要为了它们引入树、堆或复杂索引；数据库查找和历史分页才需要索引。资格用位掩码，可用位运算判断是否参与、弃牌后移除及人数统计。

权威数据只保存必要事实：余额、普通贡献、费用记录、折牌标记、牌与行动历史状态。总底池、可跟注额、当前全下标记、可获奖的普通池等可以派生，不能维护多个互相可写的总数。冻结报价与附加池原始资格属于必须保存的历史事实，不能事后重新推导。

规则处理先复制这一份小状态形成候选，再验证和提交。每房间允许同时存在权威状态、候选状态与一个序列化缓冲的预算；不保留每个历史版本的完整 Python 对象。

## 4. 牌型查表与机器人缓存

现有三张牌评分可编码为不超过 uint16 的整数。若使用 27×27×27 的直接查表，共 **19,683** 项；每项两字节为 **39,366 字节，约 38.4 KiB**。重复牌位置可作为无效哨兵，不会在合法评估中使用。

完整两底三公只需九次三张评分查表取最大。摊牌每个玩家算一次完整牌力，再用于所有奖池，不为每个边池重复生成牌型。没有必要预先构造所有多人布局或把数百万种对局放入内存。

Python tuple 的查表存储会比紧凑数组大，但仍很小；应比较实际速度再选择，不以压缩几十 KiB 牺牲可读性。真正需要限制的是蒙特卡洛整手评分缓存：现有 fast_score 的 LRU 上限为 65,536，它的复合元组键和 Python 对象可能占数十 MiB，并在每个工作进程复制一份。

建议新机器人默认先测试无缓存与 **4,096 条有界 LRU**，记录命中率和峰值内存后再调整。牌面高度随机时，低命中缓存可能只有内存成本。共享常量在工作进程启动时构建一次；不随每个任务重复传入整张查表。

机器人任务只含本人观察和有界公开历史，单任务编码目标不超过 16 KiB。首版两工作进程，最多两项执行和八项等待；每个房间最多一个当前机器人任务。逾期结果丢弃，禁止旧任务覆盖新回合。

## 5. 房间、连接与日志预算

| 资源 | 建议界限 | 达到上限后的处理 |
| --- | --- | --- |
| 每房间指令邮箱 | 64 项，客户端最多占 56 项，保留内部消息余量 | 入队失败明确返回繁忙；不能算已接受动作 |
| 单条入站消息 | 16 KiB，且字段另设数量与长度限制 | 在解析和入队前拒绝 |
| 单连接出站 | 最多 16 条且总计不超过 64 KiB | 关闭慢连接，重连取最新投影；不阻塞房间提交 |
| Socket 框架入站缓冲 | 建议最多 4 条、每条 16 KiB | 网络背压及速率限制；实际库行为需压测 |
| 房间内公开事件环形缓冲 | 最多 128 条，序列化总量最多 128 KiB | 丢弃最旧缓存；数据库仍保留需要的历史 |
| 客户端本地历史 | 最多 256 条，界面先渲染最近 50 条 | 滚动分页加载，不把所有旧 DOM 留在牌桌 |
| 浏览器权威快照 | 1 份最新快照 | 旧版直接替换；动画只持有必要的小事件 |
| 前端待呈现动画 | 最多 32 条短事件 | 重连或落后时跳到最新状态，不无限追播 |
| 幂等回执内存缓存 | 每房间最多 256 项 | 超出后查数据库；不能因此忘记已成功动作 |
| 结束房间保留 | 完成后建议内存保留 10 分钟 | 卸载 actor；按需读取只读结果 |

历史列表不是隐私豁免：公开缓存不放别人的底牌或牌库顺序。数据库中供恢复使用的私有事件不能直接作为网页回放响应。

队列容量只限制缓冲，不限制一局合法加注次数。程序不能因为动作达到一个人为阈值而直接判玩家失败。超过预期的自动推进次数应报告内部错误并冻结该房间等待恢复，不能部分发奖后继续。

## 6. 单节点内存规划

规划目标为 100 个活跃房间、每房间五个主连接，共 500 个玩家连接。实际约束还有只读标签页和旁观者；首版不开放无限旁观，额外连接必须计入总数。

| 项目 | 估算预算 | 说明 |
| --- | --- | --- |
| 100 份房间状态及候选副本 | 3—10 MiB | 按每房间最多约三份 8—32 KiB 状态预算 |
| 100 个邮箱、回执缓存与公开事件缓存 | 120—400 MiB | 包含消息积压预算；Python 解析对象会比序列化载荷大，缓存须按界限淘汰 |
| 500 个 Socket 与收发缓冲 | 80—200 MiB | 依赖 WebSocket 库、TLS、操作系统缓冲与慢连接比例 |
| API 解释器、框架、数据库驱动和其他运行时 | 80—180 MiB | 待用部署镜像实测 |
| 两个机器人工作进程 | 160—400 MiB | 含解释器、查表、任务及受限缓存；不靠 fork 共享假设预算 |
| 余量 | 至少上述估算的 30% | GC、高峰序列化、重连与临时对象 |

据此建议 API 与机器人合计先给 **1—2 GiB 的资源配额**，而不是因为牌只有 27 张就承诺几十 MiB 足够。PostgreSQL、反向代理和操作系统另算；同机初期可从 **4 vCPU／4 GiB** 开始开发验证，容量承诺必须以压测为准。

消息大小与队列长度需要一起预算：100 个房间的外部队列都积压 56 条、每条达到 16 KiB 时，仅原始载荷就有 **87.5 MiB**，还未计解析对象和缓存。实际下注指令通常很短，但不能据此忽略拥塞上界；协议必须拒绝未知字段并限制字符串长度，不接收任意嵌套 payload。压测同时记录原始字节、解析对象及进程 RSS，若触及配额就降低准入容量，不能靠无界缓冲维持表面在线。

浏览器端不预存所有牌局快照，不加载大幅位图牌面。SVG 花色、CSS 卡牌与少量字体可控制静态资源；游戏数据自身目标在数 MiB 内，整个标签页内存还包含浏览器和 React 基线，不能拿 JSON 大小代替总内存。

## 7. 磁盘、事务与带宽

首版每个已接受动作在一个事务中追加事件、记录幂等回执并更新最新快照。快照只保存最新版本；历史行为用事件记录，不为每个动作永久保存一份完整快照。必要时每局结算额外留一个调试检查点，作为单独、可裁剪的策略。

容量计算示例，均为假设而非实测：

- 假设每局平均 30 条已接受动作，12 局约 360 次提交；这不是合法动作上限。
- 若每次提交新增事件平均合计 1.5 KiB、回执 0.5 KiB，一场约新增 720 KiB 历史载荷。
- 最新私有快照若为 8 KiB，每场保存占用约 8 KiB，但更新 360 次会产生约 2.8 MiB 的快照逻辑写入。
- 每天 10,000 场，历史原始载荷约 6.9 GiB／天；加上索引、行头和膨胀，预留量可能是数倍。
- WAL、备份与快照更新会继续增加写入量，不能把 6.9 GiB 当作总磁盘或每日写入上限。

建议首版完整对局记录保留 7 天用于排错，整场结果保留更久，具体期限由产品需求确定。去重回执至少保留至本场结束后的重试窗口；活动场次的回执不可按短 TTL 提前删除。删除历史与快照、回执的先后必须保证结束房间不再接受游戏动作。

网络初始选择是每次动作广播按接收者生成的完整小快照，不先做复杂增量协议。若一份投影 4 KiB，一次动作给五人发送约 20 KiB；100 房间平均每房间每 5 秒一个动作，则约 20 动作／秒，即 **100 份玩家投影／秒，约 400 KiB／秒**，未计协议头与重传。峰值、机器人快局和重连会显著提高这个数。

全量投影需有 16 KiB 的目标上界，历史采用分页，不能越玩快照越大。客户端重连取得当前状态和有限历史，动画不要求重放每一个丢失的视觉帧。

## 8. 算法复杂度与循环边界

| 操作 | 工作量 | 设计选择 |
| --- | --- | --- |
| 洗牌 | O(27) | 每局一次 |
| 找下一行动者 | 最多扫描 5 席 | 保持固定 seat 与短顺序表 |
| 生成普通贡献层 | O(5 log 5) | 对五个贡献值排序，最多五层 |
| 冻结全部改航报价 | 最多 5 人×5 层 | 精确整数分子分母计算，避免浮点上取整错误 |
| 单人摊牌牌力 | 9 次三张评分 | 每人只算一次，复用于所有池 |
| 普通池及附加池分配 | 最多约 10 池×5 人 | 先按资格合并，再分配余筹 |
| 机器人 S 次采样 | 约 O(S×存活人数×9)，改航估三种选择 | 是首要 CPU 热点，应放进程池而非事件循环 |
| 单房间下一动作等待 | 阻塞于异步队列／计时器 | 没有忙等，没有每房每秒全量扫描 |

下注响应不是“每人固定操作一遍”，必须保存 pending 名单直到跟齐、弃牌或全下。一次加价至少增加一个整数筹码，同一下注轮目标有界，玩家最多五人；轮内无任意取回筹码行为，因此正常合法动作会推进。新输入触发下一步，不在一个函数内同步等待真人完成整轮。

自动推进只处理发牌、退款、报价、跳过无法行动者和结算等有限步骤。建议设内部 64 步诊断保护；这个数是实现故障保护，不是用户可利用的回合规则或加注上限。

## 9. 实施后必须测的指标

| 指标 | 初始验收目标 | 口径 |
| --- | --- | --- |
| 普通动作纯规则计算 | p95 小于 5 ms | 不含网络、DB 与机器人；实际机器上测 |
| 动作入队至提交回执 | p95 小于 150 ms，p99 小于 500 ms | 单节点目标负载，含队列与事务，不含公网延迟 |
| 事件循环延迟 | p99 小于 50 ms | 机器人运行时同时观测 |
| 原型机器人决策 | 通常小于 500 ms | 给定样本数与硬件；超预算回退，不阻塞房间 |
| 持续内存 | 30 分钟稳定运行后不单调增长 | 同时检查 actor、Socket、任务及缓存数量 |
| 慢客户端 | 不拖慢同房其他人 | 填满出站队列后断连并能重连恢复 |
| 断线与恢复 | 不重复付费，不改变洗牌结果 | ACK 丢失、进程崩溃、DB 提交响应丢失分别测 |

压测至少包含 100 房间均为真人节奏、20 房间连续机器人动作、500 连接同时重连、慢接收者与重复指令洪峰。先记录吞吐、延迟与内存，再决定增加机器人进程、拆分机器人服务或对房间分片。

未来多进程／多节点必须先设计房间归属与 fencing token，数据库拒绝过期拥有者写入。直接把 Uvicorn workers 从 1 调到 4 会产生四份各自独立的房间字典，不能作为当前架构的安全扩容方案。

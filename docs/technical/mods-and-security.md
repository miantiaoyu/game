# Steam 多人与 Mod 安全设计

版本：设计稿 v0.2 · 2026-10-09  
产品前提：独立 3D Steam 多人游戏；服务端负责权威牌局。  
规则基线：[标准牌局规则 v1.0](../standard-rules.md)。  
交付范围：威胁模型、模组分类、权限契约、包锁定与故障设计。本轮不实现客户端、Mod SDK、沙箱、Steam 接入或反作弊模块。

## 1. 安全目标与信任边界

**官方游戏由官方控制的专用服务器执行规则和结算；客户端、房主和下载到的 Mod 都不能修改权威状态。** 房主拥有创建房间、邀请和选择允许的开局配置等产品权限，不因“房主”身份获得发牌、查看底牌、退款或修改结算权限。官方模式不把玩家设备作为可决定结果的 listen server。

客户端可以被修改、调试或替换，玩家可能重放网络消息、伪造金额、篡改界面、运行辅助程序或同时使用多个账号。3D 牌桌的模型、相机、动画、碰撞与物理结果只负责表现；把筹码模型拖到桌中央、翻开牌背网格或修改本地余额，不构成合法指令，更不能直接推动发牌或扣款。

| 威胁来源 | 可能的行为 | 核心防线 | 仍然存在的边界 |
| --- | --- | --- | --- |
| 修改后的客户端 | 越权看牌、错误金额、乱阶段行动、伪造随机结果 | 最小信息下发、严格指令校验、服务器洗牌与事务提交 | 无法保证玩家不改自己已知信息的显示方式 |
| 恶意房主 | 指定牌序、临时改费用、强占他人座位 | 官方服务器独立授权，开局锁配置，控制权与房主管理分离 | 玩家可以选择退出或在外部串通 |
| 非可信 Mod | 越权读牌、执行代码、消耗资源、读取本机文件 | 数据型首版、能力白名单、资源导入限制；未来隔离执行 | 内容需要审查和版本撤销，哈希本身不保证安全 |
| 网络重放与故障 | 重复付款、旧局动作、断线后回滚、洪峰请求 | 幂等键、版本及行动机会校验、截止时间、限额队列 | 延迟影响体验，不能让客户端时间决定截止 |
| 恶意社区服务器运营者 | 偷看全牌、偏置发牌、伪造结果 | 与官方可信环境分隔、显著标注运营者及自定义状态 | 玩家自有服务器无法被本游戏的客户端协议证明诚实 |
| 服务端权限失陷 | 数据库或调试权限泄露全牌 | 最小运维权限、审计、密钥与私密快照隔离 | 此设计信任官方服务运行边界；并非对恶意运营者的密码学公平证明 |

Steam 身份验证解决连接者身份及相关访问资格问题；网络加密或中继解决部分传输与连接问题。它们不验证“这次加注是否超过底池”“改航费是否冻结”“某人是否有边池资格”。这些规则校验必须由游戏自己的服务器实施。Steam 平台标识也不代表某个客户端程序、Workshop 内容或房主值得信任。

## 2. 官方标准、自定义规则与社区运行分区

| 环境 | 运行与准入 | 对外标识 | 结果地位 |
| --- | --- | --- | --- |
| 官方标准房 | 官方专用服务器；固定标准规则摘要和受认可的表现资源 | “官方标准 · 规则 v1.0” | 可作为未来官方统计来源；首版不据此承诺排行榜功能 |
| 官方托管自定义房 | 仍由官方服务器执行；只接受允许的声明式参数及精确锁定的包 | “自定义规则”，列出与标准不同的参数 | 不混入标准房统计或未来排名 |
| 未来社区自托管房 | 社区运营服务器，可能运行更广扩展 | “社区服务器 · 非官方运行环境”，公开规则与运营者 | 不导入官方可信结果；相同规则名也不等于官方可信 |
| 本地练习／调试 | 用户自己的进程，可以使用固定种子和调试工具 | “本地练习／调试” | 不上报官方对局结果 |

官方标准资格由服务端发行版本、规则内容摘要和允许的包集合共同确定，不能由房主勾选“标准”或客户端上传标签取得。自定义房与标准房在房间发现、加入确认、整场记录和未来统计入口均分开。

服务器端不能装载“客户端要求加载的任意文件”。即使两名玩家订阅了同一个 Mod，官方服务器仍只认可自己的允许目录、能力契约和已验证内容摘要。下载是否完成只影响客户端能否呈现并加入，不赋予它修改服务器配置的权限。

## 3. 隐藏信息与数据投影

官方服务器保存真实洗牌结果、未公开底牌、牌库游标和用于恢复的私密状态。洗牌使用服务端安全随机来源；离线实验种子不得作为联机公开种子。恢复消费原来确定的牌序，不重新洗牌。

每个接收者的视图都通过字段白名单生成。**不得向客户端预发全牌再依赖加密开关、隐藏对象、材质、UI 遮挡或本地逻辑防止翻看。** 已全下不提前公开底牌，弃牌不公开底牌；正式摊牌只发布规则允许公开的信息。

| 接收方 | 允许接收 | 禁止接收 |
| --- | --- | --- |
| 玩家连接 | 本人两张底牌、已揭公牌、公开弃牌、公开行为、筹码与池资格、本人合法动作 | 对手未公开底牌、牌库余序、洗牌种子、其他人的私有机器人采样 |
| 淘汰者／旁观投影 | 公共桌面、公开历史、正式摊牌结果 | 仍未公开的他人底牌或局后自动解密全部牌序 |
| 客户端资源 Mod | 已投影的表现标签、公开事件、本地允许的材质／声音选择 | 原始服务器状态、网络会话密钥、牌库；不得提供额外取牌接口 |
| 声明式规则配置 | 经校验的公开常量 | 状态对象、数据库、任何实时底牌 |
| 服务端机器人 | 该机器人本人的底牌和与真人同等的公共观察 | 其他人的底牌、真实未来牌序；不能因为与引擎同机运行就拿全量状态 |
| 未来策略脚本 | 指定座位的过滤观察、合法动作、受限公开历史 | 私有内核对象、任意座位观察、未来随机流 |

资源系统不能通过对象名称、排序键、网络实体 ID、贴图索引、动画预加载、声音或不同资源下载路径暗示未揭牌。公牌对象的真实牌面只在相应公开事件提交后出现；牌背资源不应根据隐藏牌型选取。当前玩家自己的客户端始终能访问其本人已知底牌，这属于必要信息，不能宣称防止其用外部工具分析。

普通日志记录命令类型、脱敏玩家标识、版本、事件范围、拒绝原因和公开结果。不要记录 Steam 身份票据、会话凭据、原始私密快照或隐藏手牌。异常日志、崩溃转储、性能采样及客服诊断上传也属于潜在泄露路径：默认不导出敏感内存，受限调试须有访问控制、留存期限和审计。服务器私有快照只供受权恢复服务读取，不进入客户端 Mod 目录、Steam Cloud、Workshop 包或公共回放。

公开动作历史仍完整保留行动者、阶段、下注金额、改航顺位、费用、改航／放弃、目标位置及实际换出／换入牌。为性能缓存而分页或淘汰本地记录，不等于删除服务端必要审计记录。不能为了防辅助而删掉真人正常决策所需的公开信息。

## 4. 指令校验、幂等与反滥用

玩家只能提交动作意图，例如“跟注”“本次新增投入 20”“替换公位 1”。客户端不得提交可信的中奖金额、自己计算的费用、自己声称的胜率、新牌、结算赢家或目标池资格。

服务器在持久化事务之前验证：

1. 核对身份、应用访问资格及房间访问权限；此时不先检查当前控制连接或行动权。Steam 验证的具体会话建立和失效处理按接入时的 SDK 文档实现。
2. 以 `(room_id, principal_id, command_id)` 查回执；相同语义的成功重试返回原结果，同 ID 不同语义拒绝。
3. 仅对尚无原回执的新指令，核对当前控制连接、`controller_epoch`、`match_id`、`turn_id`、`expected_revision`、服务端接收时限与该玩家当前行动权。
4. 对动作和金额进行严格类型与范围校验；底池上限、短额全下、重新加价权、冻结改航费及余额均从权威状态计算。
5. 在独立候选状态中推进并检查筹码、卡牌、阶段与池资格不变量；提交成功后再广播接收者投影。

通过身份与房间访问检查后，成功动作重试先查回执，不能因版本已推进或控制权已经转移而误报失败。失败或超时的候选不能留下已扣款、已消耗牌、已创建边池等半成品。发牌和结算只能由服务器内部命令触发，房主接口不提供绕过入口。

区分传输攻击、非法游戏意图与普通网络故障。按连接、账号、房间以及受约束的来源维度限制消息大小、速率、并发连接、历史分页及待处理队列。不能只按 IP 限制，误伤同网玩家；也不能仅按账号限制后允许匿名握手无限创建资源。具体数值由容量文档与压测确定，不在 Mod 子系统另开无限消息通道。

反复提交无效金额、旧机会指令和洪峰消息可以触发降速、断开连接或人工审查，但一次过期版本、断线重发、策略选择不佳不能自动证明作弊。对局进行中不接受客户端发来的“重新结算”“回到上一局”或“重新发相同种子”。回放只能只读重现已提交事件，不得重新触发付款。

## 5. Mod 分类与首版承诺

**当前承诺设计声明式参数 Mod，并为被动视觉资源定义安全边界。任意规则代码、客户端 DLL 和服务器脚本运行不是首版能力。** 以下分类是能力范围，不是下载文件扩展名的区别。

| 类型 | 可表达内容 | 首版状态 | 核心限制 |
| --- | --- | --- | --- |
| 视觉与声音资源 | 牌背、桌面、筹码外观、被允许的音效、局部装饰 | 可作为受验证的被动资源范围；导入流程仍待实现 | 不带运行时代码；不改变隐藏信息、命中判定、支付金额或合法按钮 |
| 声明式规则 profile | 已列入 schema 的整数参数及已实现的离散选项 | 首版规则扩展设计范围 | 服务器校验并编译为内建规则配置；不得含表达式、反射类型、任意脚本或 URL |
| 沙箱规则／策略脚本 | 新规则建议或基于过滤观察的动作建议 | 未来能力，需独立安全与确定性验证 | WASM 或受操作系统限制的进程；能力白名单与硬配额 |
| 原生插件／任意程序集 | DLL、共享库、引擎插件、任意托管程序集 | 不作为官方 Mod 加载方式 | 不能由 Workshop 内容直接注入客户端或权威服务器 |

### 5.1 被动资源

资源包仅能引用批准的素材格式、固定的资源入口与内建材质模板。纹理／网格／音频在隔离导入流程中做格式、尺寸、长度和复杂度校验，生成可被游戏安全读取的产物；资源解析器本身也需要维护和补丁。不要将带任意 MonoBehaviour、原生导入器、脚本或自定义 shader 的引擎工程包直接视为“贴图”。首版使用内建 shader 加受限参数，避免以 GPU 程序绕过“无脚本”承诺。

自定义牌面只能改变合法可见卡牌的表现，不可以通过不同牌背向玩家表达服务器未发给他的真实牌。官方标准房可进一步限制高干扰素材、可读性不足或遮挡其他人操作提示的资源；客户端本地外观允许清晰回退到内建资源，不改变真实对局结果。

### 5.2 声明式规则 profile

参数配置提交给服务端后，由版本化 schema 校验，再转换成内建不可变 `RuleProfile`。样例可以声明“继承标准＋差异参数”，但加载时须把默认值和继承链展开为完整有效配置，再计算参数配置哈希；不能依赖未来会变化的标准默认值。没有“执行配置中的公式”步骤。下面与领域文档统一的候选 v1 工程上限仍待实现验证；它们不改变官方标准的每人100、总500、12局：

| 参数域 | 候选范围 | 必须保持的不变量 |
| --- | --- | --- |
| 整场局数 | 1—100 局 | 不允许无限局；局数影响历史量、恢复及资源预算，须联合验证 |
| 逐局底注计划 | 长度等于局数，每项为受 profile 金额上限约束的正整数 | 明确每局费用，不执行表达式；全下和不足底注仍有定义 |
| 初始筹码 | 每席 1—10000 枚，自定义房全员相同；总量至多50000 | profile 单独保存初始总量用于守恒；整场无补币接口，不能沿用标准总量500作唯一校验 |
| 改航方向 | 仅选择内核已有的正向／反向 | 不引入任意状态机跳转或多次额外窗口 |
| 首末改航费率 | 有界整数 bps，首费率不大于末费率，最终范围由领域 schema 校验 | 使用内建精确整数插值、向上取整、最低正底注和窗口冻结算法；每次实际改航费仍非零 |
| 六类牌型优先级 | 六种内建牌型的完整排列，无缺失／重复 | 只变类别先后，不新增牌型定义、改数字比较或脚本化判牌 |

这些自定义参数不会进入官方标准房。加载时严格拒绝布尔值冒充整数、浮点金额、零或负底注、溢出值和不完整计划，并验证发给所有玩家的底牌、三张公共牌及最多五次改航的牌库容量足够。某参数即使数值合法，也可能与其他参数组合不兼容；还须检查组合条件、整数中间计算、状态推进上界、持久化／历史容量及预计资源消耗。50000总筹码与100局必须进入新的容量验收，不能沿用标准500筹码、12局的测试结论。

v1结构能力固定五个绝对座位、27 张牌、两张底牌、三张公牌、九种合法最终组合及现有池账本。增加玩家数、牌数、底牌数、新牌型定义／脚本、无限回合、额外改航窗口或不同货币，不是简单改 JSON 即可支持的事项；它们要求升级 `capability`、schema、领域不变量、网络投影和容量测试。既有客户端遇到未知结构能力应拒绝加入，并解释不兼容原因。

## 6. Workshop、包身份与锁定

Steam Workshop 作为发现、分发和更新渠道，不作为执行权限或安全结论。订阅某个 `PublishedFileId` 只定位一个发布条目；同一条目内容会更新，条目 ID、作者显示名、订阅状态或下载成功都不能代替内容校验。官方准入还需独立的发布者策略、允许清单或审核结论。

### 6.1 规范化 manifest 与内容摘要

使用三个不同的摘要表示静态内容、有效配置和本场实际执行环境。它们可以使用 SHA-256 等成熟摘要算法，但不能全部混称为“包哈希”。文件路径、JSON 规范化、依赖排序及摘要域标识都是版本化协议的一部分。

| 摘要 | 精确定义 | 何时改变 |
| --- | --- | --- |
| `rule_package_hash` | 包本身的静态文件清单、规范化 manifest 及锁定依赖内容 | 文件、manifest 或静态依赖改变；房主单独选择另一组有效参数不必改变同一静态包摘要 |
| `rule_profile_hash` | 已展开继承与默认值的完整有效规则配置 | 实际生效参数改变，即使仍使用同一静态包 |
| `rule_lock_hash` | 组合上述两项摘要与本场实际引擎构建、运行时、SDK／ABI、批准能力和确定性配置的锁清单摘要 | 任一实际执行条件改变；在整场开局时固定，恢复时核对原锁 |

下表列出**整场规则锁的输入**，不是一个文件的摘要，也不是把所有运行时配置都塞入 `rule_package_hash`：

| 规则锁输入 | 说明 |
| --- | --- |
| 静态包与文件清单 | 通过 `rule_package_hash` 绑定规范相对路径、长度、文件摘要和manifest；涵盖全部可加载文件 |
| 锁定依赖图 | 静态依赖通过包摘要绑定；核对每个直接／传递依赖的精确内容，拒绝依赖环、浮动分支和缺失文件 |
| 实际启用配置 | 通过 `rule_profile_hash` 绑定全部有效参数与展开后的默认值；同包不同配置产生不同规则锁 |
| 实际 Mod SDK／ABI 版本 | 锁定钩子、字段、值编码和状态序列化契约的具体版本；不能只写“兼容最新版” |
| 已批准权限与结构能力 | 明确每个能力及资源上限；不得超出静态manifest声明，批准范围扩大也要重新准入并生成新锁 |
| 实际运行时与执行契约 | 锁定运行时具体版本、确定性配置、允许宿主函数；无脚本时明确为 data-only |
| 实际宿主构建 | 锁定本场规则引擎／服务构建及适配层具体版本，并验证静态manifest的兼容范围 |

各摘要与签名字段不循环参与其自身摘要；签名验证针对约定的摘要及发布元数据。签名证明发布来源和未被篡改，不证明作者行为良善；已签名恶意包仍可被撤销准入。

建议区分规则锁与客户端资源锁：改变本地音量或内建显示偏好不改变规则身份；影响规则的配置、依赖、SDK、权限和运行时必须进入规则锁。自定义房要求一致的资源依赖时，在资源锁中明确列出；不可把仅改了皮肤的房间悄悄归入不同规则，也不可借“只是皮肤”绕过必要规则摘要。

### 6.2 加载和开局

1. 房主在准备阶段选择自定义 profile，服务端解析受允许的包与配置，生成完整锁清单；向所有参与者公布规则差异及身份。
2. 客户端通过批准渠道取得必要资源，校验锁清单和能力兼容，展示下载／拒绝原因。客户端声称哈希匹配不是可信的远程完整性证明；无论是否声称校验成功，权威规则均只由服务端执行，服务端校验自己的包与锁。
3. 服务端确认准备及准入后锁定本场的规则摘要、依赖、配置、SDK、能力、具体运行时与引擎构建；开局后禁止热更新、依赖漂移和按玩家私下变参。
4. Workshop 在后台更新时，当前场继续使用已锁定的不可变产物；新内容只能在后续准备流程生效。

服务端及客户端要防止目录穿越、绝对路径、符号链接逃逸、重复规范路径、大小写混淆、压缩炸弹和依赖放大；下载到 staging 目录，全部验证后才原子提升为可用包。包中的远程 URL 不自动下载执行，外部依赖必须经锁清单与批准下载器取得。

### 6.3 恢复、撤销与回放

私有状态快照保存精确规则锁及必要的可序列化扩展状态。恢复只能使用原来的包字节、配置和兼容的已锁定执行环境；不能因为条目已经更新而改用 latest 重算下一动作。服务端要在允许恢复的期限内留存原产物，避免“数据库还在、规则包已删”的不可恢复状态。

如果原运行时存在安全问题，不能为了恢复硬启动已确认危险的包，也不能悄悄替换语义。该场暂停为可审计的故障状态，按下面的终止／人工处理流程解决；未来若支持迁移，须有明确版本迁移器、结果验证与记录。

规则回放默认用于受权服务端审核。分享给玩家或 Mod 的回放仍经过信息投影，不因为牌局结束就自动解密所有弃牌和牌库。公开回放不具有再次调用付款或写状态接口的能力。

## 7. 扩展 API 与能力白名单

所有钩子由宿主在规定边界调用，参数为复制或序列化的 DTO，不暴露内核对象引用、数据库连接、网络套接字或反射入口。以下是设计契约名称，未实现，也不是开放给插件任意调用的万能 RPC。

| 能力／钩子 | 输入 | 允许的输出 | 禁止行为与状态 |
| --- | --- | --- | --- |
| `profile.validate` | manifest、声明式参数、宿主能力清单 | 校验结果与由宿主生成的标准化配置 | 首版由内建校验器执行，不调用包内任意代码；不得读牌或网络 |
| `presentation.resolve` | 已允许的表现标签、经投影的公开事件、合法资源 ID | 本地贴图／网格／声音等引用 | 只读资源映射，不读真实牌库，不新增服务端指令，不触碰结算 |
| `rules.describe` | 已锁定的公开规则配置 | 规则摘要、参数说明与本地化键 | 不能伪装标准房标签，不能通过文案替换实际规则 |
| `policy.propose_action`（未来） | 指定座位过滤观察、合法动作、受限公开历史、确定性随机输入 | 一个带机会版本的动作建议，或明确无建议 | 无法修改状态；建议再走同一指令验证；不读取其他座位私密观察 |
| `rules.propose_modifier`（未来） | 宿主批准的阶段、已公开局面、白名单参数范围 | 有界的候选规则修饰量 | 不直接扣筹码／移牌／建池／判赢家；能力未授权时宿主拒绝，不自动扩权 |
| `extension.save_state`／`load_state`（未来） | 该扩展自己的版本化状态字节 | 有上限的状态数据或校验失败 | 不读宿主内存、不写任意路径；状态不包括真实牌库或他人底牌 |
| `telemetry.emit`（未来） | 模组自己的错误码与有界数值 | 经宿主审查的诊断条目 | 无任意网络上报、任意字符串手牌导出或访问完整崩溃内存 |

首版不存在允许第三方替代服务端牌型比较、洗牌、牌库游标、余额写入、退款、主边池建账或结算的钩子。未来需要扩展这些结构能力时，必须重新设计信任边界；不能把一个“不允许直接扣钱”的脚本接入点逐渐变成任意状态 mutation。

建议的脚本观察不包含未来随机结果。向策略脚本提供的确定性随机输入必须与真实牌库随机流隔离，知道该输入也不能推出未发牌。所有允许的宿主调用、输入和返回值都可以被规则回放审计，但私密座位输入仍属于受限记录。

## 8. 未来沙箱与资源配额

`AssemblyLoadContext` 解决程序集装载和卸载等运行时组织问题，不构成恶意代码安全沙箱。不要把任意托管 DLL 在同一权威进程中加载后，凭“没有把数据库对象传进去”就认为它不能访问文件、网络或进程内存。客户端也不允许 Workshop 包带任意 DLL／原生库自动执行。

未来脚本有两条候选路线，届时测量并选择一种明确支持的运行环境，不能默认两者都已安全实现：

| 方案 | 必需的边界 | 宿主注意事项 |
| --- | --- | --- |
| WASM 运行时 | 显式导入白名单、线性内存上限、指令 fuel／中断、输出与调用次数上限；默认无 WASI 文件／网络能力 | WASM 格式本身不保证正确配置；维护运行时漏洞补丁，禁止动态暴露宿主函数 |
| 独立受限进程 | 专用低权限身份、只读包目录、受限临时空间、无外网出口、无宿主凭据、OS CPU／内存／进程数限制、超时强制终止 | “单独开一个进程”不等于沙箱；不得与权威进程共享完整状态、数据库凭据或任意 IPC |

WASM 可以再放入受限进程作为纵深隔离，但需要单独计算资源成本。隔离进程控制自己的模组对象，不拥有对局权威；进程崩溃不能直接使房间状态变成半提交。

| 资源 | 必须设置的限制 | 初始预算建议与验证方式 |
| --- | --- | --- |
| 包下载与展开 | 压缩量、展开量、文件数、单文件大小、依赖深度、总依赖体积 | 数据型规则 profile 可先限制为 64 KiB；资源包按批准内容预算，不能仅看压缩体积 |
| 视觉资源 | 纹理尺寸与解码占用、网格顶点／面数、音频长度、shader白名单 | 导入时检查，运行时统计CPU/GPU资源；耗尽时回退内建素材 |
| 每个规则钩子 | 确定性指令／fuel预算、宿主调用次数、返回字节数 | 候选起点 5万指令、返回4 KiB；须用代表性脚本校准，不当作已测性能 |
| 每个策略钩子 | 与规则钩子分开的计算预算和服务器机会期限 | 策略允许更高但有上限的预算；任何结果不得越过原行动期限 |
| 脚本实例 | 内存页数、持久状态字节数、并发实例数 | 候选起点64 MiB内存、64 KiB持久状态；按房间与进程总额再次限流 |
| 时间与任务 | CPU预算、看门狗时间、排队长度、未完成任务数 | 确定性fuel决定脚本失败，墙钟看门狗作为逃逸／挂死保护；不能靠无限等待拖住全桌 |
| IO与诊断 | 默认零网络、只读允许包、无任意磁盘／环境变量、限额日志 | 配额超限产生固定错误码，日志截断且不输出敏感输入 |

所有限制都进入能力配置及适用的锁清单。规则脚本不能读取墙钟、系统随机数、主机路径、线程调度或不受控浮点运算作为结果来源；优先使用整数和固定算法，禁止并发共享状态。策略脚本的随机输入和任何需复现的宿主随机结果由宿主显式提供并记录，真实洗牌流与之分离。

同包、同配置、同运行时、同状态和同输入须产生相同的候选输出。确定性测试应覆盖保存／恢复与不同支持机器；若浮点或平台差异无法消除，就缩小支持运行时范围，不能把“基本一样”当作规则一致。任何墙钟看门狗触发均走故障处理，不把“某台机器快所以赢得更多计算”默认为规则的一部分。

## 9. 崩溃、超限与恶意包处理

模组输出只进入候选状态。权限拒绝、陷阱、超时、内存超限、格式错误和不变量失败，都不能形成部分扣款或消耗牌库。某次提交是否成功以数据库事务回执为准，不能在未知提交结果时盲目重跑模组。

| 故障 | 当次状态处理 | 房间与包处理 |
| --- | --- | --- |
| 准备期包缺失／摘要不符／能力不支持 | 不开局、不发牌 | 给出可操作错误；不能用另一版本代替 |
| 本地视觉资源损坏或超额 | 不影响权威牌局 | 回退内建资源；提示资源禁用，允许重新校验 |
| 首版声明式参数不合法 | 拒绝配置，不改变当前锁 | 返回字段与组合原因，不偷偷更正为另一个规则 |
| 未来策略建议非法／超时／崩溃 | 丢弃建议，当前动作仍由宿主控制 | 在原期限内允许宿主标准策略或已有的安全超时动作；这种备用策略须事先公开并记录 |
| 未来规则钩子崩溃／超额／非确定性 | 丢弃候选并保持最后已提交状态 | 该房间进入故障暂停，不悄悄禁用规则继续玩；隔离包并阻止新房准入 |
| 宿主无法确认事务是否已提交 | 暂停后续推进 | 先查持久版本与回执，再恢复；不因进程重启重复付款 |
| 恢复时原包不存在或已被安全撤销 | 不继续运行未知／危险规则 | 保留状态与审计，等待明确恢复方案；不能加载latest顶替 |

故障暂停不会把当前池主观判给某人。若无法恢复，可将整场标记为技术中止：不生成官方胜负或统计、不伪造摊牌结果，保留已提交记录，另开新场。游戏筹码仅属于该场，无外部真实余额可自动扣补；若未来加入跨场资产，必须另行设计补偿账本，本设计不预先宣称能够退款。

同一包反复失败时阻止新场加载并记录摘要、运行时、钩子和公开错误码。对玩家显示“该自定义规则运行失败”，不将失败包的内存、堆栈或输入牌局直接上传给模组作者。事故修复发布新内容身份；旧对局恢复如何兼容须明确审计。

## 10. 辅助程序与串通的能力边界

权威服务器能阻止超额下注、伪造赢牌、重复支付和通过协议偷取隐藏牌，但不能仅凭这些保证玩家没有使用本地概率计算、截图识别、外部语音共享底牌或多账号串通。Steam 身份、Workshop 禁用和加密传输都不等价于禁止场外交流。

官方规则可禁止自动决策和串通；工程上可保留公开动作及有限、合规的诊断信号，识别极端同步、异常共同账户行为或可疑长期转移，再人工复核。固定决策时长、强水平、使用某种皮肤、单次错误操作都不能单独作为作弊证据。

如果以后设计举报、处罚或反作弊 SDK，需要明确收集数据、隐私边界、误报申诉和支持平台。当前不承诺内核级驱动、不自动要求 VAC，也不宣称 Steam 强制所有多人游戏采用某一种反作弊方案。对局规则防作弊和客户端环境检测是不同层次，可独立评估。

## 11. 实施前必须验证的场景

| 验证项 | 完成标准 |
| --- | --- |
| 客户端私密信息隔离 | 截获真人、机器人、全下者、旁观者各自载荷；无法找到无权查看的底牌、余牌序或种子 |
| 3D表现与权威分离 | 修改本地筹码、对象翻面、资源和相机不会改变服务端余额、牌序或资格 |
| 指令重放 | 双击、重连、旧局、旧机会、同ID异语义、晚到机器人等均无重复或越权提交 |
| Mod准入 | 无签名／未允许、摘要错误、缺依赖、能力扩大、非法参数、结构修改均按预定策略拒绝 |
| 内容身份 | 同Workshop条目更新后摘要变化；相同依赖／配置可稳定重建锁；开局后原锁不漂移 |
| 包导入与配额 | 目录穿越、压缩炸弹、过大纹理／网格／音频、依赖环、解析器错误不能越过导入边界 |
| 恢复 | 锁定旧包仍可按原规则恢复；旧包丢失／撤销不静默换版；事务未知时先查证 |
| 沙箱（未来） | 文件／网络／环境变量／进程访问被拒绝；无限循环与内存耗尽受控；不影响其他房间 |
| 钩子原子性（未来） | 规则钩子任意位置失败，已提交状态无变化、牌库游标不额外推进、无孤立费用池 |
| 确定性（未来） | 同锁与输入跨保存恢复结果一致；支持平台间差异不会产生不同结算 |
| 环境标识 | 官方标准、自定义和社区托管不可通过客户端标签互相冒充，统计入口不混算 |
| 日志与诊断 | 常规日志、崩溃上传、模组错误报告和公开回放均不会导出私密牌局或凭据 |

历史模拟与规则测试只能帮助验证玩法内核，不能替代以上联网、包导入及隔离测试。文档中的钩子和配额在实现、故障注入与安全评估完成前，均属于设计要求。

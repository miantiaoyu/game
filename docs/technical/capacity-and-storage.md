# 资源、可靠性与发行前验证

设计 v0.2 · 2026-10-09。对象为 .NET 无图形牌局后端。下面的数值是建议预算与验收目标，尚无新服务实现或压测；v0.1 的 Python／浏览器内存估算已归档，不能当作当前实测。

## 1. 标准规则与扩展容量分开

| 数据 | 标准规则 | 参数 Mod 能力 v1 提案 |
| --- | --- | --- |
| 席位／牌库 | 5／27 | 保持 5／27；拓扑变化需新能力版本 |
| 每人底牌／最终公牌 | 2／3 | 保持 2／3 |
| 每局牌库消耗 | 最多 18 张 | 同上：10 底牌＋3 原公牌＋最多 5 替换牌 |
| 总筹码 | 500 | 从冻结配置计算，最多 50000 |
| 局数 | 最多 12 | 1…100，逐局底注计划长度须匹配 |
| 普通贡献层／费用笔数 | 各至多 5 | 同上，最终同资格池按类型合并 |
| 当前状态保留结果 | 最近一局 | 同上；完整历史按需读取，不随局数复制状态 |

规则初始筹码、局数和费率均有有效范围，禁止加载后直接执行任意长度集合或用户提供的类名。入房显示有效参数；采用能力 v1 不意味着自动支持未来更大牌库或更多座位。

## 2. 数据表示与内存预算

| 值 | 建议表示 | 理由 |
| --- | --- | --- |
| CardId／SeatId／SeatMask | byte；入口校验范围 | 标准拓扑很小；协议数值类型与内存宽度不必相同 |
| 已知牌集合 | uint，限制 27 位 | 快速集合与去重检查 |
| 筹码与普通贡献 | int32 | 为有界参数规则留空间；跨池求和与费率乘法使用 checked int64 |
| 版本／事件序号／owner_epoch | 非负 int64 | 对应 PostgreSQL BIGINT，范围不超过 2^63−1；Protobuf 编码明确 |
| SteamID | UInt64，独立于状态版本 | 不假定所有 UInt64 都可装进有符号 BIGINT；持久表示另见协议 |
| 牌库与席位数据 | 小型数组／只读封装 | 每次候选迁移复制必要容器；数组不能因外层是 record 就被当成不可变 |
| 三牌评分基础表 | 27³ 个 ushort | 原始值共 39366 字节，约 38.4 KiB；类别强弱可由规则配置映射 |
| 规则包和配置 | 按摘要缓存的只读对象 | 房间引用冻结版本，不各自复制大型包 |

标准状态目标为 16 KiB 内，规划先按每份 32 KiB 预留；私有序列化快照目标 16 KiB 内。候选状态、已提交状态及序列化缓冲分别计量，不拿数组载荷字节数代替 .NET 托管堆总量。自定义初始筹码增大不使数组变长；最多 100 项的底注计划放入共享冻结配置。

性能路径优先用清楚的短循环和有界容器。避免每次决策构造整场历史、无界 LINQ 中间集合、按全量布局永久记忆化。对象池／ArrayPool 只在剖析证实值得时使用：含私牌的归还缓冲必须清理，复用不能跨观看者暴露内容。

## 3. 并发与内存上界

| 资源 | 建议上界 | 超限行为 |
| --- | --- | --- |
| 房间邮箱 | 64 条，外部最多占 56 条 | 明确忙碌；保留内部容量，不先成功确认再丢命令 |
| 玩家单条命令 | 16 KiB | 限帧、解码递归、字段与集合长度；禁止解压后无界放大 |
| 单连接待发 | 16 条且不超过 64 KiB | 断开慢连接，重连取当前私有投影 |
| 每房间连接 | 10 条含重连／只读会话 | 准入控制；一身份只有一个有效控制连接 |
| 房间公共事件缓存 | 128 条且不超过 128 KiB | 淘汰最旧缓存，持久记录分页读取 |
| 命令回执内存缓存 | 256 条 | 未命中查持久化回执；缓存淘汰不解除幂等 |
| 机器人任务 | 每房间最多 1 个有效；每节点先用 2 执行＋8 等待 | 拒绝继续积压，按合法回退处理；CPU 密集任务不占房间执行循环 |
| 单局评分缓存 | 首先不用或限制 4096 项 | 根据命中率再调；按规则摘要隔离 |
| 规则内容缓存 | 按字节计费、限制活动版本数 | 拒绝新加载或卸载无活跃引用版本；不能卸载正在恢复所需包 |

100 个房间的邮箱都填满外部 56 条且每条 16 KiB，原始载荷已有 87.5 MiB，还未计解码对象、连接、回执及公开历史。先限字节和项数，再谈节点容纳多少房间。

建议压测起点为整个部署 100 活跃房间、500 玩家主连接；若开放额外连接，另测最多 1000 连接。采用至少两个可接管的应用实例，平时分摊负载，任一节点失效后存活节点仍须能承载全部目标负载。容量数字不应简单把两节点峰值相加而没有故障余量。

初始实验可给每个应用节点 4 vCPU／4 GiB 配额，数据库独立；这只是开始测量的配置，不是采购保证。记录总 RSS、托管堆、GC 暂停、工作线程排队、Channel 等待、数据库连接占用和机器人耗时，再确定每节点硬准入阈值。服务器不加载模型或贴图。

## 4. 循环与 CPU

一房由一个逻辑消费者推进。没有每房一条常驻 OS 线程，也没有牌局 60 Hz／120 Hz Tick；等待网络或期限时挂起。客户端每帧渲染不触发服务端状态写入。

核心计算仍很小：洗牌 O(27)，选行动者扫描至多五席，分层最多五个断点，单人摊牌九个合法组合。Mod 改牌型顺序可以映射六个强度项，不生成无界牌型代码。

下注不是固定五次操作；加注后需要继续响应。终止证明以本轮有限整数筹码为界：正额支付最多为冻结整场总量，待响应人数最多五人。标准宽松上界 2505 动作／轮只是终止证明；自定义配置按自己的总量推导，不能给玩家增加未声明的加注次数上限。

自动推进须在下一输入边界停下，设诊断步数保护捕获内部循环错误。预算耗尽是故障，需要冻结并记录；不能作为随机弃牌、重新洗牌或部分派奖的依据。

## 5. 数据库与网络成本

状态提交、事件、回执与所属租约检查位于一个事务。房间租约 heartbeat 是额外负载：100 房、5 秒一次约有 20 次续租／秒，应与动作写入、WAL 与副本延迟共同测量。

示例假设：标准每局 30 个命令、12 局约 360 次提交；新增事件与回执平均 2 KiB／次，一场约 720 KiB 原始历史。每天一万场约 6.9 GiB；JSON／Protobuf选择、索引、WAL、备份和私有加密封装会改变实际值。最多 100 局的自定义房必须另设保留与容量预算，不能继续套 12 局平均量。

最新快照覆盖更新，但更新本身仍产生 WAL 和页写入。日志禁止高基数地记录完整牌序、票据或所有命令载荷；审计私有数据放在受控存储中，访问可追溯。

若一次 viewer 投影平均 4 KiB，100 房平均每 5 秒一个动作、每房五人，约 400 KiB／秒有效广播；机器人连续快局、恢复重连和内容下载应另测。Mod 包／模型通过独立下载缓存分发，不挤入牌局命令通道。WSS 的 TCP 重传也须测高延迟与丢包下的排队，不能只测本机 RTT。

## 6. 稳定性目标与失效边界

| 项目 | 讨论起点／验收目标 | 必须说明的范围 |
| --- | --- | --- |
| 自有牌局服务可用性 | 月度 99.9% | 定义成功登录后可连接、操作和恢复的探测；玩家端到端体验另列 Steam／网络依赖影响 |
| 动作确认延迟 | 目标负载下 p95＜200 ms、p99＜500 ms | 从服务端收到并准入至持久成功回执，不含公网；纯规则计算另测 p95＜5 ms |
| 单应用节点失效 | 接管目标 30 秒内 | 租约、进程启动、加载和客户端重连总时间；跨区域灾难另定义，不混为同一承诺 |
| 应用进程故障的数据恢复 | 已确认动作不丢、不重复、不换牌 | 基于已持久提交的快照、事件和回执，演练提交前后及未知结果 |
| 数据库节点失效的数据恢复 | 依据复制／提交配置确定 RPO | 异步副本可能丢最近提交；若要求已确认动作零丢失，必须同步确认、主库 fencing 与提升流程并演练其故障范围 |
| 同房并发 | 同一时刻只有一名可提交的拥有者 | 校验数据库 owner_epoch，模拟网络分区，不能只观察内存锁 |
| 长时间运行 | 24 小时混合负载无持续泄漏、无未解释余额偏差 | GC、任务、Socket、包引用和回执清理均有指标；机器配置与负载记录 |

服务故障恢复使用协议规定的持久剩余时间及补偿上限。个人断线不冻结全桌。备份用于数据灾难恢复，不能代替实时节点接管；多应用实例也不能消除数据库单点。

生产数据库方案应包括主从、监控、受控提升与备份；跨故障域复制、同步确认的延迟及成本需在部署预算中选择。当前没有预算与服务区域数据，不能承诺区域灾难 RTO/RPO 或全球低延迟。

## 7. 发行前必须拿到的证据

1. **规则：** 标准牌型、下注重开、未匹配退款、主边池／费用池、余筹、反向报价与淘汰逐步一致；标准余额总量恒为 500。参数规则按自己的总量与范围验证。
2. **迁移：** Python 参考与新核心使用完全相同的牌序、动作和有效配置比较。发现差异先查标准规则，不能默认旧程序永远正确。
3. **故障注入：** 提交前宕机、提交后回执丢失、主库响应丢失、双节点竞争、网络分区、租约续约失败、恢复途中再次崩溃，均不能重复派奖。
4. **安全：** 伪造 SteamID、过期票据、重放、越权行动、畸形消息、Mod 篡改、隐藏信息投影与日志检查。无权客户端即使抓全流量也拿不到未公开牌。
5. **性能：** 稳态目标房间数、所有连接重连、慢消费者、机器人计算高峰、最大合法参数房与 Mod 包加载；同时进行节点故障测试。
6. **运维：** 从备份恢复到隔离环境，校验回执和规则包可用；版本排空、回滚、协议不兼容拒绝、旧规则房跨更新继续完成。
7. **Steam 联调：** 真实 Steam 身份、邀请／加入、退出／重连与测试分支更新。SDK 接口、可用区域与发行配置在实际接入时确认。

灰度先控制房间准入，只让新房进入新版；已有房间固定 engine_build 与规则包。回滚前必须检查已写入格式的向后兼容，不能只替换二进制就称数据库可回滚。

这些门槛是上线证据要求，没有在本轮执行。Python 历史测试数量、语言选择或 Steam SDK 接入都不能单独替代它们。

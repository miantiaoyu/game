# 请求防重与流量控制

设计讨论稿 · 2026-10-10。本文补充[协议、并发与恢复](protocol-and-concurrency.md)，用于明确下一阶段实现前的行为；不表示网络限流或持久化已经完成。目前已有进程内有界队列（命令与查询分别限额），以及房间内存中的命令去重和预期版本检查；回执尚未持久化。

## 1. 三个问题分别解决

| 问题 | 例子 | 主要机制 |
| --- | --- | --- |
| 一次操作被重复传输 | 加注成功但回执丢失，客户端重发 | 稳定命令编号、语义核对、持久回执 |
| 过时操作集中到达 | 连点、断网积压、旧连接迟到 | 单个待确认意图、行动机会与版本检查、控制权代数 |
| 资源被大量请求耗尽 | 恶意客户端更换命令编号刷请求 | 分层限流、每玩家占用额度、有限缓冲与并发、断开滥用连接 |

限流不能保证不重复扣款；命令编号不能阻止攻击者换编号刷包；队列不能判断谁有权行动。这些机制需要一起工作。

## 2. 正常客户端的操作状态

每个玩家在一个房间里，最多保留一个未得到确定结果的牌局修改意图。动作按钮共享这个状态，不能每个按钮分别允许一个请求。

```text
可操作 → 提交一次意图 → 等待确认 → 收到确定结果并同步状态 → 再次可操作
                           ↓ 网络异常
                     结果未知，进入恢复
```

第一次提交时分配 `command_id`，保存动作类型、金额或公牌位置，以及提交依据的 `match_id`、`turn_id`、`expected_revision`、`controller_epoch`。后续重复点击不生成更多命令，也不缓存为下一次行动。

客户端可以在提交前调整金额；提交后不允许通过改变同一个命令的内容替换原意图。本阶段不设计撤销、离线下注或自动预选行动功能。

超时未收到回执表示结果未知。重试必须保留原命令编号及原语义；采用有上限的退避与随机抖动，服务器给出重试等待建议时遵循它，不把历史点击批量发送。

断线后保存的是待确认命令资料，用于查询结果，不是一串自动补交动作。重新认证、恢复控制权和订阅后，先查询原结果并取得新视图。若需要重发原命令，也不能修改原控制代数等语义字段；已成功则返回原结果，未成功且已过期／失去控制权则明确拒绝。新机会中的新动作必须重新确认。

这些行为改善正常使用体验，服务端仍需防御修改后的客户端。

## 3. 服务端处理分层

```text
连接／来源资源限制
  → 帧及消息大小、字节速率和解析结构限制
  → 有效身份、目标房间访问检查
  → 玩家及请求类别的限流
  → 相同命令结果查询／进行中合并
  → 每玩家未完成请求额度
  → 房间有界队列
  → 房间再次核对回执、控制权、版本、行动机会、期限、规则
  → 状态＋事件＋回执原子提交
  → 成功回执与各自视图
```

早期缓存和筛选只是减少成本，不能替代房间内的权威检查。最终是否执行由当前房间拥有者和持久化事务确定。

### 接入层先控制低成本资源

未认证连接也要限制并发数量、握手频率、认证等待时间与票据验证并发。不能让大量匿名连接先占满内存或触发无上限 Steam 验证请求。

对完整消息限制字节数、解码深度、字段和数组长度；WebSocket 分片不能各自获得一份完整消息额度，还要限制消息组装时间。读缓冲、出站队列及待处理任务均有上限。既限制条数，也限制字节量。

现有单条命令 16 KiB、单连接入站最多 4 条完整消息、出站最多 16 条且不超过 64 KiB，可作为待压测起点。它们不是已证明的发行容量。

### 多个限流维度承担不同职责

- 连接：限制某个客户端实例的消息与字节速率。
- 玩家身份：合并同账号的多个连接，重连不清空其限制预算。
- 请求类别：登录、牌局修改、视图／回执查询、历史查询分别限制。
- 房间：防止该房间的总消息和待处理任务过多。
- 节点／入口来源：限制总连接和总工作量，IP 作为辅助维度，不作为唯一身份。

建议用令牌桶吸收有限的短时突发，同时限制持续速率；具体每秒额度在网络实现和压测阶段确定。限流身份来自已验证会话，不能按客户端自报的玩家编号建预算。

只按 IP 会误伤同一网络下多人，只按连接则可通过重连绕过。多节点部署时身份预算需要稳定归属或受协调的总额度，不能每换节点就领取一份新额度；单房间的成员额度由其唯一拥有者管理。

限流命中先明确拒绝或要求退避，持续超量可断开相应连接；不是一次重复、旧版本或短时突发就封禁玩家。大量拒绝日志聚合计数，不能为每条恶意消息无限写日志或数据库。

## 4. 去重既核对编号，也核对内容

唯一键沿用 `(room_id, principal_id, command_id)`。语义指纹包含协议语义版本、整场、动作参数、预期版本、行动机会和控制权代数；不包含连接编号及重试次数。使用规范化语义，不直接把原始 Protobuf 字节当成唯一含义。

| 已知情况 | 处理 |
| --- | --- |
| 原命令已提交，编号与内容相同 | 返回原回执，不重新执行 |
| 原命令正在排队／执行，编号与内容相同 | 合并到原操作或返回处理中，不再入队 |
| 编号相同但内容不同 | 返回命令冲突，不覆盖原操作 |
| 没有原记录 | 在限流和占用额度内尝试接收，再执行权威校验 |

进行中记录的登记与占用额度必须原子协调；队列满而未接收时要释放登记和额度。不能先留一份“处理中”记录再因为入队失败让它永久挂起。

合并也需要限制：不能给同一个命令挂无限等待者／响应任务。可以按受限连接数返回一个进行中状态，由受限查询或后续回执结束等待。重复请求仍消耗入口预算，缓存命中并不意味着免费无限回复。

已认证并通过房间访问检查后，**先查原回执，再判断当前版本、行动机会、控制权和期限**。否则成功下注后状态已推进，回执丢失重试会被错误报告为失败。查询已执行结果的权限不等于执行新动作的权限。

持久回执与筹码变化在同一事务提交。内存缓存淘汰后仍可查持久记录；进程崩溃后不依赖内存 HashSet 记忆已经扣过款。原事务提交结果未知时，必须由房间恢复流程核查，不能把一次未查到记录理解成确定未执行。

## 5. 新编号也不能重复消费同一次行动机会

恶意客户端可以为同一次点击连续生成新 ID，因此仅靠去重不够。

新动作必须匹配当前房间、整场、行动机会、版本、有效控制权、截止时间和具体规则。一条成功动作消费了当前机会后，后续旧机会请求不能作用于新的机会。

加注后未来可能再次轮到同一个人，但那是一个新的 `turn_id`；“还是同一局／同一轮下注”不能作为复用旧机会的理由。

`expected_revision` 校验可能因其他合法房间状态变化而拒绝旧视图请求。客户端需要刷新并让玩家重新确认，不能自动把旧动作改成新版本后继续执行。条件校验必须在房间实际处理时再次完成，不能只在网关读一个可能过时的缓存。

## 6. 一个人不能占满房间队列

建议首版对同玩家、同房间最多接收 **一个尚未完成的牌局修改请求**。查询使用独立的小额度和频率限制；同一请求的重发不再消耗新的队列项。

额度跟随已接收操作，直到处理明确结束后释放。客户端断线、关闭等待或旧连接失效，不能立即释放它，让重连再塞一条重复操作。进程／拥有者切换后按持久状态和原命令恢复，不依赖旧连接的内存状态。

这个限制是请求占用限制，不是每局只许操作一次；操作完成并进入新的合法机会后可以再次提交。查询、重连控制权认领和原命令结果恢复需要受限的独立通路，不能被一个长期未确认请求永久堵死。

房间总等待上限仍然需要，但它是最后一道保护。正常 2～8 人回合制场景不应靠积攒几十条下注维持运行。接受加入等尚未成为成员的请求也必须有限额，不能通过访客绕过房间预算。

## 7. 超时、翻牌与故障

翻公共牌一般是当前动作触发的自动规则迁移，和下注结束、阶段变化一起生成候选状态并提交。无需等客户端发“翻牌”命令，也无需从消费循环里再排一条消息等自己处理。

独立的行动超时与恢复事件使用设计中的内部预留额度：64 个队列位置中外部最多 56，预留 8 给内部事件。内部生产者也必须有数量上限；预留空间满时在消费循环之外异步等待，保持事件有效性，不丢弃或无限创建任务。

预留额度不等于允许超时插队。健康拥有者按成功入队的服务端单调时间和序号判断动作是否按时，截止时间相等视为过期；不能相信客户端发送时间。按时入队的请求不会仅因数据库排队在截止后处理而自动失效。

若客户端消息在网络里滞留，到达时已经过期，不能追溯执行。若房间消费能力或数据库出现可确认故障，则进入服务恢复和计时补偿流程。单个玩家刷请求或自报“我卡了”不能触发全桌无限暂停；仅靠队列满也不能断言服务故障，须结合持久提交、调度延迟和健康检查判断。

TCP 可以保证连接内传输有序，但并不代表下注业务恰好执行一次；断线重建、回执丢失和业务重试仍需要上述协议。客户端断线也不意味着原服务器事务已经撤销。

## 8. 一次网络卡顿的预期行为

玩家在机会 T17 中提交“新增投入 20”，命令编号 C100。

1. 客户端进入待确认状态，接下来的十次点击不产生十条新命令。
2. 服务端提交 C100，保存状态、事件及回执，扣款一次。
3. 响应没有送达，客户端不能确定结果。
4. 网络恢复后，以 C100 查询或按原语义重试。
5. 服务端返回 C100 的原成功结果，并发送当前视图，不再次扣款。

如果 C100 当时没到服务器，恢复时 T17 已经过期，则返回机会已过期，不补扣、不把它当成新机会的动作。

如果错误／恶意客户端发送 C101～C200，一部分会在入口被限流，一部分被玩家未完成额度拒绝；即便有请求进入房间，也必须检查原机会是否仍有效，不会把这些消息当成连续一百次下注。

旧连接迟到消息在接管前可能已合法提交，因此恢复时必须查结果；接管成功后，旧控制代数不能再提交新动作。两条连接的到达顺序不应改变已经提交的结果。

## 9. 回执含义必须明确

| 结果 | 含义 | 客户端如何处理 |
| --- | --- | --- |
| Applied | 已持久提交，返回原命令和提交版本 | 同步权威视图，不重复执行 |
| Pending | 已知同一命令尚未确定结果 | 有限等待／查询，不创建新意图 |
| Busy／RateLimited | 本次没有新接收，需退避 | 保留原编号；若此前发送结果未知，仍需核查原命令 |
| Recovering | 服务暂时无法确定／推进 | 等待恢复，不猜结果 |
| 机会过期／版本不符／非法动作 | 这个新动作被明确拒绝 | 刷新视图，由玩家决定新动作 |
| 无响应／连接断开 | 不知道结果 | 恢复身份后核查原命令 |

Busy 指本次尝试未新增接收，不能据此证明同编号的更早一次请求没有提交。Pending 也不是成功确认。当前进程内队列的任务完成不具备这里的 Applied 持久语义。

## 10. 实现前需要列入验收的情况

1. 连续点击、相同命令重复发送、多连接同时重发，最多产生一次效果。
2. 相同编号不同金额被拒绝，旧回执不变。
3. 每次换新编号刷旧机会，仍只能执行有效机会允许的动作。
4. 已提交但回执丢失、提交途中断线、服务器崩溃，恢复后不重复扣款／发牌。
5. 重连后旧连接迟到，不能夺回操作权或回滚客户端视图。
6. 队列满、每玩家额度满、缓冲超限均给出明确处理，不积累无限任务或日志。
7. 一个玩家大量查询／非法操作，其他玩家仍能在目标预算内操作；多账号／未认证连接压力也分别测试。
8. 集中重连采用退避与抖动；身份验证、查询、响应发送均不会形成新的洪峰。
9. 正常网络延迟、丢包、临界截止时间、服务故障分别处理；不能把普通重试判成作弊。
10. 拒绝消息、命令回执和监控记录不泄露其他玩家底牌、令牌或秘密牌序。

观察指标至少包括按原因的拒绝量、每玩家待处理数、房间队列深度／最老等待时间、处理与提交延迟、去重命中、查询负载、断线／重连、超时与服务恢复次数。速率和容量阈值以这些验证结果调整。

下一步应先定义命令身份、行动机会、回执语义与玩家请求状态，再逐步实现去重和限流。仅增加一个“每秒最多 N 次”的判断不足以满足上述约束。

## 设计约定

改代码前逐条对照。

1. **业务拒绝与故障分开。** 输入格式合法、但当前状态不允许的操作，抛 `规则拒绝异常`，并且抛出前不能改动任何状态。执行器只把这一类当作正常拒绝；其他异常都视为状态可疑，停止该房间。
2. **按来源对错误分类。** 客户端可以控制的值（座位号等）出错，属于规则拒绝。认证层或可信流程提供的值（玩家编号、牌序）出错，属于服务端缺陷，抛 `ArgumentException`。格式检查放在命令构造或入队前完成。
3. **枚举数值是对外协议。** `拒绝原因`、`房间阶段` 只能追加成员，已有成员不改名、编号不复用。
4. **一个事实只存一份。** 参与顺序显式保存，不从底牌张数推算；阶段显式保存，不从字段是否为空推算。
5. **输入先复制，再交出只读视图。** 只读视图不能是可强转回数组的原数组；`Array.AsReadOnly` 在构造时调用一次。
6. **先构造新值，成功后再一起赋值。** 失败时对象保持原状态。
7. **修改只能经由 `房间.执行(命令)`。** 具体的修改方法是 `internal`。执行器独占 `房间` 实例；把房间交给执行器后，调用方不能再直接使用它。
8. **命令处理顺序固定：** 先查原结果，再查版本，最后执行规则。拒绝也要记录，重发时得到同样的拒绝；编号冲突不记录，以免覆盖原结果。
9. **只读查询不走命令。** 查询不改版本、不去重，但同样要排队，才能看到先前提交的修改。
10. **任务成功不等于已保存。** 当前没有持久化，`await` 成功只代表内存状态已改变。
11. **筹码只记“每个座位的累计普通投入”，奖池是派生值。** 主池、边池、连环全下全部由这一个数组算出（`奖池划分.划分普通池`）。任何地方都不单独保存“池总额”作为真相，否则两者迟早对不上，主池／边池也再算不出来。
12. **改航费单独记账。** 它不抵跟注、不提高下注上限、资格名单在窗口开始时冻结（规则 5.3），不能混进累计普通投入。
13. **退还未获跟注的超额在每轮关闭时做**，不是等到结算（规则 4.5）。它会改变后续轮的余额与底池上限。
    退款完成后的不变量：**最高投入额至少被两人持有**。这条不变量保证顶层不会出现“无人跟过的池”，
    边池划分也就不需要专门处理“一人独得顶层”的畸形态。
14. **外部边界一律用英文标识符**：协议字段、数据库列名、配置键、日志字段、URL 路径。中文只用于规则层与房间层的领域词汇。

## 已知限制

- 命令记录只在内存里保留最近 128 条，进程重启就会丢失。接入数据库后，回执要和状态在同一个事务里保存。
- 编号冲突的判断只看命令内容。设计中还要比较玩家身份（唯一键包含 `principal_id`），这要等认证接入后才能做。
- 还没有"每个玩家最多一个未完成命令"的额度，一个玩家仍可能占满 56 个命令名额。
- 同一编号的重发仍会再占一个排队名额。设计要求把它合并到正在排队的原命令上，这一点还没实现。
- 内部事件（超时）的 8 个预留名额，等计时功能实现时再加。
- 房间还没有持有整场，因此一局只能发一次底牌、没有下注；整场与多局流程未开始。
- 下注轮已经能独立运行，但还没接进单局，也没有行动机会（`turn_id`）。
- 每轮关闭时的退还未获跟注超额尚未实现。

## 编码与命名

源码目录、类名、变量名使用中文，便于对照规则原文。这依赖 UTF-8：

- `.gitattributes` 固定文本换行符（LF），避免 Windows 检出后出现整文件假改动。
- 若 `git status` 把中文路径显示成 `\346\272\220\347\240\201`，在本机执行一次
  `git config core.quotepath false`（这是本地配置，不会随仓库分发）。
- 源文件是 UTF-8 无 BOM。**不要用会把文件另存为本地代码页的编辑器**（某些 Windows 编辑器默认如此），否则整份文件乱码。
- `LANG=C` 的容器或 CI 里，处理中文路径的 shell 脚本容易出错；脚本尽量按字节匹配，或显式设置 UTF-8 环境。
